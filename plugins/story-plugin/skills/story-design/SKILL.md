需求拆解，帮助用户理解需求，生成 slug，探索代码，澄清问题，创建目录，输出文档。

## 设计规则

- 与项目有关的设计，代码，规则等，加载 `.agent/library/overall.md` 这个文件获取知识。
- 当需要设计C++代码，加载 `.agent/library/common/ue5-cpp-rule.md` 获取规范

### Phase 0 检查 Epic / TDD 上下文（可选）

- 如果用户提供了 Epic 文档路径或提及了某个需求点编号：
  1. 读取 Epic 文档（`.agent/story/<slug>/Epic_*.md`）
  2. 定位到对应的需求点章节，提取已有的需求描述作为初始输入
  3. 将 Epic 中该需求点的完整内容作为 Phase 1 的起点，跳过已明确的部分
  4. 向用户确认：「Epic 中的需求描述是否仍然准确？有无需要修改？」
- 如果用户提供了 TDD 文档路径或提及了 TDD：
  1. 读取 TDD 文档（`.agent/story/<slug>/TDD_*.md`）
  2. 提取已有的技术设计描述作为初始输入
  3. 将 TDD 中的内容作为 Phase 1 的起点，跳过已明确的部分
  4. 向用户确认：「TDD 中的描述是否仍然准确？有无需要修改？」
- 如果没有 Epic 或 TDD 上下文，正常进入 Phase 1。

### Phase 1 理解需求

- 根据如下的流程工作，每一步都需用户确认。在用户未确认时，等待用户确认。

从如下角度进行需求理解
  - 需求的目的
  - 需求的设计边界，功能边界，
  - 需求的测试方式，测试场景

**不要**设计到具体的代码细节，本阶段只对其需求和用户意图

**必须**向用户提出澄清问题，并与用户对齐需求理解。
**必须**得到用户的明确确认，才能进入下一步。

### Phase 2 设计

设计原则：
- **不会就问**：如有疑问，**必须**可向用户询问，**禁止**替用户进行假设
- **设计最小原则**：每个设计必须明确其目的，**禁止** "以防万一"式冗余设计，
- 从程序和策划角度评估是否需要 CVar 调试接口（开关、强制触发、数值覆盖等）
- 提供配置思路
- 罗列配置所用到的功能
- 实现方式，配置方式
- **配置资产说明**：如果设计涉及需要配置的资产（如行为树、PhysicsControlAsset、AnimMontage、DataAsset、DataTable 等），**必须**给出具体的配置步骤和关键参数说明，让策划或程序能照做
- 根据指导文件，去工程目录探索，了解代码的实现方式，配置方式，测试方式，测试场景
- 考虑网络同步

**必须**得到用户的明确确认，才能进入下一步。

### Phase 3 更新设计文档

- 提炼 ≤5 词中文短语作为目录名（如 `怪物推挤`），向用户确认。
- **写文档前判断**：检查当前上下文中是否已提供了需求文档（用户贴入的、或对话中已引用的 `.agent/story/` 下的文档）。
  - 若已有需求文档：**必须**询问用户「更新现有文档」还是「新增一份文档」，并给出现有文档路径供参考。
  - 若无已有文档：直接新建。
- 文档方式：目录 `.agent/story/<slug>`，统计已有文档数 N，新文件命名 `需求<N+1>_<功能名>.md`。
- 加载 `./references/document-template.md` 来生成文档。
- 文档写完或更新后，提醒用户打开文件确认，并提示当前文档路径。
- 提示用户：可进入实现阶段或 Review 阶段。
