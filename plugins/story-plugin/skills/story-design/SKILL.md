# 核心前置：自动化上下文检索
- **若本次会话尚未读过** `${CLAUDE_SKILL_DIR}/../common/basic.md` 与 `${CLAUDE_SKILL_DIR}/../common/gamedesign.md`，则加载一次；已加载则跳过。
- **静默探索**：进入 Phase 1 前，先自动使用 `fd`/`rg` 在工作区检索关联的 `TDD_*.md` 或是其他前置需求文档。若存在，直接提取其中的需求/技术设计作为本任务的既定事实起点，跳过重复确认。

### Phase 1: 需求理解与方案设计（UE5 策划视角）
1. 融合用户当前输入与前置探索到的 TDD/需求信息。
2. 梳理核心功能边界、测试用例，**不涉及具体代码实现细节**。
3. 找出所有未决的设计分歧或与前置文档冲突的地方。
4. **唯一打断点**：将初步的设计梳理结果输出，并集中抛出需要澄清的问题。**等待用户确认后再进入下一步。**

### Phase 2: 输出标准化设计文档
收到用户确认后，按以下精简模板结构生成最终的 `<需求标题>.md`，并同步更新 TDD 文档（若有变更）。完成后，提示用户“可进入代码实现阶段”。

> **文档生成规范与模板结构**：
> - **1. 需求简介**：一句话核心描述。
> - **2. 功能说明**：融合策划目标与技术行为。
>   - **2.1 边界条件**：表格列出特殊情况/异常处理。
> - **3. 配置项**：列出 DataAsset 中的可配置参数（文件位置、类型、默认值）。
> - **4. 接口设计**：核心接口 C++ 声明。每个接口**必须包含注释**说明用途和参数含义。蓝图接口用 `> [!tip]` 说明调用方式。
> - **5. 实现方案**：
>   - **5.1 涉及文件**：表格列出相关类/模块。
>   - **5.2 类图结构**：使用 `<mermaid classDiagram>` 绘制新增/修改的类、结构体及其关系，包含关键属性和方法。
>   - **5.3 功能模块**：拆分子章节，简述逻辑/目标/角色。使用 callout 标注性能/兼容性等风险。
>     - **5.3.X.1 伪代码**：接口/函数单独代码块，前置一句话说明职责。
>     - **5.3.X.2 图示**：优先选择流程图。如果设计的模块非常多，可以考虑使用时序图表达。简单功能直接跳过。
> - **6. 调试接口 / 7. 蓝图使用说明 / 8. 待确认事项**：（如不涉及，直接整章跳过）。
> - **9. 变更记录**：仅保留 `<YYYY-MM-DD HH:mm>：初始创建/修改`。
