# 核心前置准备
- **前置**：加载 `${CLAUDE_SKILL_DIR}/../common/basic.md`（同会话已读则跳过）。

# Phase 1: 需求分类与确认

根据用户的输入，严格分流处理：

### 场景 A: 正式需求 (Story) 
* 触发条件：用户提供了明确的需求/设计文档。
* 执行动作：
  1. 按 `basic.md` 的「Slug 检索流程」定位目标 slug 目录（用户未指定时主动询问）。
  2. 读取需求文档，重点阅读「实现方案」、「涉及文件」与「伪代码」章节。
  3. 若用户当前的修改意图与文档设计冲突，**禁止直接实现**，须调用 `/story-design` 重新设计并等待审批。
  4. 严格遵循文档中的接口设计（函数签名、参数、返回值）进行编写。

### 场景 B: 临时需求 (Quick)
* 触发条件：用户无既定文档，仅口头提出代码修改。
* 执行动作：
  1. **绝对禁止**直接修改目标源文件。
  2. 必须先在对话中清晰输出具体的修改方案（如伪代码或 Diff 预估）。
  3. 静默等待，直到用户明确回复确认后，方可操作文件。

# Phase 2: 完成与交付

代码编写/修改完成后，必须向用户清晰提示以下内容：
1. 当前关联的需求文档路径（若有）。
2. 本次已修改/新增的源文件列表。
3. 提示用户：“可进入 Review 阶段，或继续修改代码”。
