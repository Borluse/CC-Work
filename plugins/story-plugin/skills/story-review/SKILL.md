# 核心前置与工具
- **必须** 加载 `${CLAUDE_SKILL_DIR}/../common/basic.md` 获取必要信息。
- **强制要求**：使用 `ue5-reviewer` agent 进行 Review。
- **上下文检索**：优先通过 `fd`/`rg` 检查当前分支或暂存区内活跃的 `需求文档.md` 或代码文件。若上下文极度明确，直接进入 Step 1，无需向用户追问类型。

# Step 1: 执行双轨制审查

仅对**本次需求相关**的内容进行审查，严禁超纲。根据审查类型，严格按 R1, R2, R3 统一编号，并对标以下维度：

| 审查类型 | 核心审查维度（严禁漏项） |
| :--- | :--- |
| **设计 Review** | 需求边界完整性 / 接口最小暴露原则 / 图文一致性 / 配置项合理性与默认值 / 联机同步方案与关键风险 / 是否有更简洁替代方案 |
| **代码 Review** | 代码与需求文档一致性 / 健壮性与死锁性能 / 跨平台兼容性（DS、手机、编辑器） / 接口最小暴露 / 是否符合项目编码规范 |

# Step 2: 生成并输出报告

在当前目录下（或用户指定位置）生成一份 Review 报告。文档结构强制遵循以下标准模板：

```markdown
# 需求 [设计/代码] Review 报告
* 关联需求：`<需求文档.md>`
* Review 日期：<YYYY-MM-DD HH:mm>
* 涉及文件：<文件列表>（仅代码 Review 填写）

## 总体评价
<总结整体质量、主要风险及值得推广的优点/良好实践>

## 问题清单
> **表头规范**：
> - 设计 Review 使用：`# | 章节 | 问题描述 | 建议修改`
> - 代码 Review 使用：`# | 文件 | 行号 | 问题描述 | 建议修改`

### 🔴 必须修改
### 🟡 建议修改
### 🟢 可选优化

## 结论
- [ ] 通过（设计：可进入实现；代码：可以提交）
- [ ] 有必须修改项，修改后重新 Review
```

# Step 3: 闭环提醒与迭代
将生成的报告完整呈现在对话中，并提示用户查看。

询问用户：“哪些问题需要现在修复？”

修复与更新：收到用户明确的修复指令后，方可外科手术式修改代码。修复完成后，必须同步更新 Review 报告中的状态，重新向用户输出最新报告，直到所有 🔴 项清空。
