# 核心前置与工具
- **前置**：加载 `${CLAUDE_SKILL_DIR}/../common/basic.md`（同会话已读则跳过）。
- **上下文检索**：按 `basic.md` 的「Slug 检索流程」定位目标 slug 目录后，在该目录下用 `fd`/`rg` 或 `ast-grep` 检索 `需求文档.md` 与相关代码文件。若上下文明确，直接进入 Step 1。
- 询问用户是review 代码还是review 设计

# Step 1: 执行审查
仅对**本次需求相关**内容审查，严禁超纲。审查条目统一采用 `R+递增数字` (如 R1, R2) 编号。对标以下维度：

- **设计 Review** : 需求边界完整性 / 接口最小暴露 / 图文一致性 / 联机同步方案与风险 / 替代方案评估 
- **代码 Review** : UE5 规范 (GC安全、宏标签分配、RPC验证) / 代码与需求一致性 / 性能与死锁风险 / 跨平台兼容性 / 接口最小化 

# Step 2: 委托 ue5-reviewer 生成报告
- 创建或使用一个团队成员 `reviewer`，团队成员的agent为 `ue5-reviewer`

**主 Agent 必须将找到的文件路径和需求上下文清晰传递给 `reviewer`**。由 `reviewer` 使用 Write 工具落盘报告为 `.md` 文件。
- **命名规范**：`需求N_<标题>_设计review.md` 或 `需求N_<标题>_代码review.md`。
- **写入位置**：同需求文档目录的Review子目录下。
- **迭代更新要求**：若文件已存在，`reviewer` **必须先读取该文件**，在保留原有已修复记录的基础上更新状态，严禁盲目覆盖。

文档结构强制遵循以下模板：

```markdown
# 需求 [设计/代码] Review 报告
* 关联需求：`<需求文档.md>`
* Review 日期：<YYYY-MM-DD HH:mm>
* 涉及文件：<文件列表>

## 问题清单

### 🔴 必须修改 (阻断性问题)
| 编号 | ... | ... | ... |
| :--- | :--- | :--- | :--- |
| R1 | ... | ... | ... |
### 🟡 建议修改 (优化与隐患)
| 编号 | ... | ... | ... |
| :--- | :--- | :--- | :--- |
| R1 | ... | ... | ... |
### 🟢 可选优化 (或已修复项)
| 编号 | ... | ... | ... |
| :--- | :--- | :--- | :--- |
| R1 | ... | ... | ... |

```

# Step 3: 闭环提醒与迭代
主 Agent 收到写盘完毕反馈后，仅向用户输出：报告路径 + 🔴/🟡/🟢 统计数量 + 总体结论一句话。严禁复述全文。

询问用户：“哪些问题需要现在修复？”

收到修复指令后，方可修改代码。修复后再次委托 ue5-reviewer 执行复查，原地读取并更新原报告（将修复项移至🟢并更新时间），直至 🔴 清零。
