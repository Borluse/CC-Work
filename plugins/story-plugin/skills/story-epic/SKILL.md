大需求拆分：接收一个大的开发需求，整体分析后拆成多个独立的 story 需求点，识别复用/依赖关系，输出规划文档。

- 加载 skills/common/basic.md 获取知识

### Phase 1 理解大需求

- 根据如下流程工作，每一步都需用户确认。在用户未确认时，等待用户确认。

从如下角度理解大需求：
  - 大需求的整体目标（如"一个什么样的 Boss"）
  - 涉及的核心玩法机制
  - 已知的技术约束或限制
  - **现有系统盘点**：先探索代码库，列出已有的相关系统/模块/基类，明确哪些可以直接复用、哪些需要扩展、哪些确实需要新建
  - 与现有系统的关系（复用哪些、扩展哪些、新增哪些）

**不要**深入单个需求点的细节，本阶段只做整体理解。

**必须**向用户提出澄清问题，并与用户对齐理解。
**必须**得到用户的明确确认，才能进入下一步。

### Phase 2 拆分需求点

拆分原则：
- **⚠️ 复用优先，拒绝造轮子**：拆分前**必须**先探索现有代码库，确认系统中是否已有满足（或部分满足）需求的功能、模块、基类、工具。能复用的绝不重写，能扩展的绝不新建。每个需求点必须注明「复用现有 / 扩展现有 / 全新开发」
- **独立可交付**：每个需求点应能独立设计、独立实现、独立测试
- **粒度适中**：一个需求点 = 一次 story-design 能完成的范围
- **识别共用模块**：多个需求点依赖的共用系统/模块，必须拆为独立需求点
- **不遗漏基础设施**：如需新的基础类、配置框架、通用工具，单独作为需求点
- **不会就问**：如有疑问，**必须**向用户询问，**禁止**替用户假设

对每个需求点产出：
1. 需求点名称（≤5 词中文短语）
2. 一句话描述（核心目标）
3. 功能范围（做什么、不做什么）
4. 整体方案思路（技术方向、关键决策，不涉及具体代码设计）
5. 依赖的其他需求点（如有）
6. 预估复杂度（低/中/高）
7. 风险与待确认事项

**不要**写具体的接口设计、类图、伪代码，这些留给 story-design。

最终输出：
- 需求点清单表格
- 依赖关系图（mermaid graph）
- 每个需求点的整体方案说明
- **建议实施顺序**：根据依赖关系拓扑排序，被依赖的优先

**必须**得到用户的明确确认，才能进入下一步。

### Phase 3 输出 Epic 文档

- 提炼 ≤5 词中文短语作为目录名（如 `新Boss开发`），向用户确认。
- **写文档前判断**：检查 `.agent/story/<slug>/` 下是否已存在 Epic 文档。
  - 若已有：**必须**询问用户「更新现有文档」还是「新增一份」。
  - 若无：直接新建。
- 文件命名：`.agent/story/<slug>/Epic_<名称>.md`
- 加载 `./references/epic-template.md` 来生成文档。

文档写完后：
- 提醒用户打开文件确认
- 展示需求点清单和建议实施顺序的摘要
- 提示用户：**可逐个调用 `/story-design` 针对各需求点进行详细设计**，建议按照实施顺序进行
- 提示用户：共用模块建议优先设计
