# Phase 1

# Phase 2
- 根据如下流程工作，每一步都需用户确认。在用户未确认时，等待用户确认。

从如下角度理解大需求：
  - 大需求的整体目标（如"一个什么样的 Boss"）
  - 涉及的核心玩法机制
  - 已知的技术约束或限制
  - **现有系统盘点**：先探索代码库，列出已有的相关系统/模块/基类，明确哪些可以直接复用、哪些需要扩展、哪些确实需要新建
  - 与现有系统的关系（复用哪些、扩展哪些、新增哪些）

**不要**深入单个需求点的细节，本阶段只做整体理解。

**必须**向用户提出澄清问题，并与用户对齐理解。
**必须**得到用户的明确确认，才能进入下一步。

### Phase 3 拆分需求点

拆分原则：
- **⚠️ 复用优先，拒绝造轮子**：拆分前**必须**先探索现有代码库，确认系统中是否已有满足（或部分满足）需求的功能、模块、基类、工具。能复用的绝不重写，能扩展的绝不新建。每个需求点必须注明「复用现有 / 扩展现有 / 全新开发」
- **独立可交付**：每个需求点应能独立设计、独立实现、独立测试
- **粒度适中**：一个需求点 = 一次 story-design 能完成的范围
- **识别共用模块**：多个需求点依赖的共用系统/模块，必须拆为独立需求点
- **不遗漏基础设施**：如需新的基础类、配置框架、通用工具，单独作为需求点
- **不会就问**：如有疑问，**必须**向用户询问，**禁止**替用户假设

对每个需求点产出：
1. 需求点名称（≤5 词中文短语）
2. 一句话描述（核心目标）
3. 功能范围（做什么、不做什么）
4. 整体方案思路（技术方向、关键决策，不涉及具体代码设计）
5. 依赖的其他需求点（如有）
6. 预估复杂度（低/中/高）
7. 风险与待确认事项

**不要**写具体的接口设计、类图、伪代码，这些留给 story-design。

最终输出：
- 需求点清单表格
- 依赖关系图（mermaid graph）
- 每个需求点的整体方案说明
- **建议实施顺序**：根据依赖关系拓扑排序，被依赖的优先

**必须**得到用户的明确确认，才能进入下一步。

### Phase 4 生成文档

- **语言简洁**：每个功能先用 1~3 句自然语言描述做什么、怎么触发、核心逻辑，再用图表辅助
- **前置条件用文字**：不要用列表堆砌条件，用一句话串联说清楚
- **图示优先**：判定逻辑用 mermaid flowchart，时序流程用 mermaid sequenceDiagram，参数/配置用表格
- **mermaid 节点文本要短**：避免长变量名或函数签名，缩写或用中文概括，确保渲染不溢出
- **禁止伪代码**：所有逻辑用 mermaid 图或文字描述，不写代码块（接口签名除外）
- **禁止哲学说明**：不写"这样设计的好处是..."、"这体现了..."等主观评价
- **不含实现文件列表**：Wiki 面向使用者，不列源码文件路径
- **实事求是**：只写源文档中有的内容，不推测、不补充未提及的功能
- **图示规则**：禁止时序图，类图等程序图，只使用流程图表达逻辑

#### 格式规范

- 一级标题：系统名称
- 二级标题：章节编号 + 名称（如 `## 1. 需求简介`）
- 三级/四级标题：子功能编号 + 名称
- 章节间用 `---` 分隔
- 表格对齐，mermaid 代码块标注语言
