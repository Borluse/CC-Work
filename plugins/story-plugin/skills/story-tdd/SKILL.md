# 文档规范
- **语言简洁**：每个功能先用 1~3 句自然语言描述做什么、怎么触发、核心逻辑，再用图表辅助
- **前置条件用文字**：不要用列表堆砌条件，用一句话串联说清楚
- **图示规则**：判定逻辑用 mermaid flowchart，参数/配置用表格；只用流程图，禁止时序图/类图等程序图
- **mermaid 节点文本要短**：避免长变量名或函数签名，缩写或用中文概括，确保渲染不溢出
- **代码块规则**：优先用图示表达逻辑，必要时可用无行号的纯伪代码概括，严禁含行号或具体实现细节的真实代码块
- **禁止哲学说明**：不写"这样设计的好处是..."、"这体现了..."等主观评价
- **实事求是**：只写源文档中有的内容，不推测、不补充未提及的功能


# Phase 1 准备

1. 确认 slug
2. 读取 `原始需求.md`，如果没有，则提示用户提供原始需求

# Phase 2 整体理解与对齐

从如下角度理解大需求：
  - 大需求的整体目标（如"一个什么样的 Boss"）
  - 涉及的核心玩法机制
  - 已知的技术约束或限制
  - **现有系统盘点**：探索代码库，列出已有的相关系统/模块/基类，明确哪些可以直接复用、哪些需要扩展、哪些需要新建

**不要**深入单个需求点的细节，本阶段只做整体理解。
**必须**向用户提出澄清问题，并与用户对齐理解，得到明确确认后才能进入下一步。

# Phase 3 需求拆分

拆分原则：
- **⚠️ 复用优先，拒绝造轮子**：能复用的绝不重写，能扩展的绝不新建
- **独立可交付**：每个需求点应能独立设计、独立实现、独立测试
- **粒度适中**：一个需求点 = 一次 story-design 能完成的范围
- **识别共用模块**：多个需求点依赖的共用系统/模块，必须拆为独立需求点
- **不遗漏基础设施**：如需新的基础类、配置框架、通用工具，单独作为需求点

对每个需求点产出：
1. 需求点名称（≤5 词中文短语）
2. 一句话描述（核心目标）
3. 功能范围（做什么、不做什么）
4. 整体方案思路（技术方向、关键决策）
5. 与现有系统的关系（**复用现有 / 扩展现有 / 全新开发**）
6. 依赖的其他需求点（如有）
7. 预估复杂度（低/中/高）
8. 风险与待确认事项

**不要**写具体的接口设计、类图、伪代码，这些留给 story-design。

最终输出：
- 需求点清单表格
- 依赖关系图（mermaid graph）
- 每个需求点的整体方案说明
- **建议实施顺序**：根据依赖关系拓扑排序，被依赖的优先

**必须**得到用户的明确确认，才能进入下一步。
