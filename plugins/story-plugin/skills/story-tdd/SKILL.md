# 1. 统一文档与图示规范
- **极简前置**：用 1~3 句自然语言说清核心机制（触发条件 → 状态转换 → 结果），不堆砌列表。
- **强制图示规则**：只允许使用简洁的 `mermaid flowchart`（判定节点用短中文概括，严禁变量/函数名溢出）。**绝对禁止**时序图、类图等复杂程序图。
- **伪代码边界**：仅在表达极其复杂的业务逻辑时使用**无行号的纯伪代码**概括大体方向，严禁包含真实实现细节和具体接口设计。
- **严禁主观评价**：不写“这样设计的好处是...”等哲学/主观说明。实事求是，不盲目推测或补充需求。

# 2. 执行阶段

### Phase 1: 需求分类与自动化盘点
1. 确认 slug，读取 `原始需求.md`（若无则提示用户提供）。
2. 使用 `fd`/`rg` 探索现有代码库，找出相关的已有系统/模块/基类。
3. **分流判定**：判断当前需求属于 **[A. 怪物类需求]** 还是 **[B. 通用通用系统需求]**。

### Phase 2: 一站式拆分与整体对齐（核心卡点）
> AI 将整体理解与拆分同步进行，拒绝多次打断。
根据“复用优先、独立交付、粒度适中”原则完成拆分，并向用户一次性输出以下内容进行对齐确认：
1. **大需求整体目标与技术约束**、现有系统盘点报告（明确复用/扩展/继承关系）。
2. **需求点清单表格**（包含：名称、一句话目标、功能范围、方案思路、预估复杂度及风险）。
3. **实施依赖图**（`mermaid graph` 拓扑排序）。
4. **拟采用的文档模板章节结构**（由 Phase 1 的分流结果决定）。

⚠️ **必须停下来，等待用户对上述拆分和结构的统一确认。**

### Phase 3: 格式化输出 TDD 文档
用户确认后，严格根据分流类型套用以下结构输出最终的 TDD 规划文档：

#### [分支 A: 怪物类 TDD 结构]
- **1. 怪物概述**（核心玩法、技能清单及背景简述）。
- **2. 制作方案规划**（蓝图/AI/动画状态机等常规与非常规技术点盘点，不展开细节）。
- **3. 技能制作拆解**（标准技能合并描述。每个技能包含：简介、释放条件与默认CD、流程图示、简略配置方向、资源需求与性能考量）。

#### [分支 B: 通用系统 TDD 结构]
- **1. 需求简介**（核心机制总览流程图）。
- **2. 现有系统盘点**（类名、位置、关系表格：扩展/复用/继承）。
- **3~N. 各需求点技术方案**（设计意图、配置项表格[类型/默认值/说明]、流程图、关键约束 Callout）。
- **最后一章. 实施顺序与依赖**（依赖图、实施顺序表）。
- **变更记录**（初稿说明）。
