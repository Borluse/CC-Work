# 核心前置与上下文
- **前置**：加载 `${CLAUDE_SKILL_DIR}/../common/basic.md` 与 `${CLAUDE_SKILL_DIR}/../common/gamedesign.md`（同会话已读则跳过）。
- **上下文检索**：按 `basic.md`「Slug 检索流程」定位 slug 目录，读取 `原始需求.md` 与 `总览.md`（若存在）作为需求基线。

# Phase 1: Bug 录入与关联

## 1.1 信息收集

从用户描述中提取：
- **Bug 现象**：实际发生了什么
- **复现步骤**：如何触发（若用户未提供则询问）
- **期望行为**：应该怎样（参考关联需求文档描述）
- **关键词**：从描述中提取 3~5 个核心名词，用于后续关联搜索

## 1.2 关联需求搜索

### 第 1 层：当前 Slug 内扫描（必做）

列出 Bug 归属 Slug 目录下的所有需求文档，**仅扫描文件名，不读取内容**：

```bash
fd -e md . .agent/story/<milestone>/<slug>/ --max-depth 1
```

将结果按类型分组展示：
- TDD 文档
- 需求文档（`需求N_*.md`）
- 总览文档

**默认全部列为候选项**，用户可取消不需要的。

### 第 2 层：同 Milestone 跨 Slug 搜索（必做）

用 Bug 描述中提取的关键词匹配其他 Slug：

```bash
# 列出同 milestone 下所有 slug 目录
fd . .agent/story/<milestone>/ -t d --max-depth 1

# 对每个非当前 slug，用关键词匹配文件名
fd -e md . .agent/story/<milestone>/<other-slug>/ --max-depth 1 | rg -i "<关键词>"
```

**匹配度计算**（简单规则，不读文件内容）：
- 目录名命中关键词 = +2 分
- 文件名命中关键词 = +1 分
- 按 Slug 维度汇总得分，降序排列
- 只展示得分 > 0 的候选

多个关键词分别搜索，结果按文件路径去重合并。

### 第 3 层：跨 Milestone 搜索（按需）

仅当用户提及「之前某个版本」「上个迭代」或 Bug 可能与历史需求相关时触发。流程同第 2 层，遍历其他 milestone 目录。

**默认不执行**，仅在用户请求时展开。

## 1.3 确认关联并生成 Bug 报告

汇总搜索结果，向用户展示关联候选清单：

```
─── Bug 录入：关联需求 ───

📌 Bug 归属：<date>_<slug>

▸ 当前 Slug 内需求（默认全选，可取消）：
  ☑ TDD_*.md
  ☑ 需求1_*.md
  ☐ 需求2_*.md

▸ 跨 Slug 候选（按匹配度排序，可多选）：
  ☑ 📂 <slug-A> → 需求3_*.md
  ☐ 📂 <slug-B> → 需求1_*.md

  [搜索其他 Milestone]

▸ 确认关联？
```

用户确认后，按 `references/bug-template.md` 模板生成 Bug 报告，写入 `<slug>/Bug/BugN_<title>.md`。

**Bug 编号规则**：与需求编号规则一致，自增编号。目录下已有 `Bug1_*.md`、`Bug2_*.md`，则下一个为 `Bug3_*.md`。

**关联需求字段**记录相对路径（相对于 `.agent/story/<milestone>/`），格式：
```
- `<slug>/需求1_<title>.md` - 关联原因
- `<other-slug>/需求2_<title>.md` - 关联原因
```

Bug 状态设为 `待确认`。

# Phase 2: 根因分析

## 2.1 定位根因

探索代码，结合关联需求文档中的「实现方案」「接口设计」「边界条件」章节定位问题根因。

分析时须对照：
- 关联需求文档的边界条件表 → 是否遗漏边界处理
- 接口设计的函数签名 → 是否参数/返回值使用不当
- 伪代码逻辑 → 是否实现与设计存在偏差
- 总览中的依赖关系 → 是否存在跨模块交互问题

## 2.2 复杂度判定（关键分流点）

根据根因分析结果判定修复复杂度：

**小修（Simple Fix）**：满足以下全部条件
- 修改范围 ≤ 3 个函数
- 不涉及逻辑分支/数据结构/接口签名变更
- 不影响关联需求文档中已定义的接口契约

**大修（Significant Fix）**：满足以下任一条件
- 修改涉及逻辑分支或数据结构变更
- 接口签名需要调整
- 影响范围超过单个模块
- 修复方案与关联需求文档的设计存在冲突

## 2.3 更新 Bug 报告

在 Bug 报告中填写「根因分析」，标注复杂度判定结果及理由。

**若是小修**：在「修复方案」中简略描述方案，进入 Phase 3。
**若是大修**：输出根因分析摘要 + 大修判定理由，**等待用户确认**。确认后引导进入 `/story-design` 流程。

> **大修联动规则**：
> - `/story-design` 产出或更新设计文档时，变更记录中须标注「因 BugN 修复而更新」。
> - 设计完成后走 `/story-implement` 实现，Bug 报告「修复方案」字段记录关联的设计文档路径。
> - `/story-design` 和 `/story-implement` 完成后回到 Phase 3 验证闭环。

# Phase 3: 修复实施

## 小修路径

1. 修改代码，Bug 状态更新为 `修复中`。
2. 在 Bug 报告「修复方案」中记录修改内容（简略 Diff 或一句话描述）。
3. 遵循 document-first 规则：若修复影响关联需求文档的边界条件/接口契约，须同步更新需求文档和总览，变更记录标注「因 BugN 修复而更新」。

## 大修路径

1. 由 `/story-design` → `/story-implement` 完成修复。
2. Bug 报告「修复方案」记录关联设计文档路径。
3. 状态更新为 `修复中`。

## 修复完成

代码修改完成后：
1. 更新 Bug 状态为 `已修复`。
2. 输出：
   - Bug 报告路径
   - 关联需求文档路径（若有更新）
   - 本次修改/新增源文件列表

---

# Phase 4: 验证闭环

1. 确认修复后的代码逻辑与 Bug 报告中的修复方案一致。
2. 确认关联需求文档是否需要更新（document-first），已更新则检查变更记录。
3. 可选：走 `/story-review` 对修复代码做审查。
4. Bug 状态更新为 `已验证`。
5. 输出：`✅ BugN <title> 已验证关闭` + 修改文件清单。

# 联动规则速查

| 场景 | 规则 |
|---|---|
| Bug 涉及需求设计缺陷 | Bug 报告关联需求文档，`/story-design` 更新需求文档，变更记录标注「因 BugN 修复而更新」 |
| Bug 修复引入新需求 | Bug 报告标注「衍生需求」，引导用户走 `/story-story` → `/story-design` 流程 |
| Review 发现 Bug | `/story-review` 的 Red 项可转为 Bug 报告，共享 Review 报告的分析结论 |
| Bug 修复后总览需更新 | 修复涉及需求变更时，提醒走 `/story-consolidate` 更新总览 |
| Bug 跨 Slug | 主 Bug 报告放在影响最大的 Slug 下，关联需求字段引用其他 Slug 的文档路径 |
| 修复与设计文档冲突 | **禁止直接实现**，须走 `/story-design` 重新设计（同 `/story-implement` 的守门规则） |
