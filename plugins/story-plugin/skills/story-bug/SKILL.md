# Phase 0: 初始化环境

先调用 `/story-init`（默认 search-only 模式）。

1. 记录输出中的 `<slug_dir>` 和 `<current_milestone>`。
2. **门禁**：`/story-init` 完成前禁止进入 Phase 1；同会话已执行可跳过，但须确认上述值。
3. `<slug_dir>=N/A` → 询问 Bug 归属的已有 slug；Bug 不负责创建新 slug。

# Phase 1: 录入与关联

1. 从用户描述提取现象、复现步骤、期望行为；关键信息不足时先询问，禁止脑补。
2. 读取 `<slug_dir>` 下的原始需求、总览和需求文档，建立需求基线。
3. 按 Bug 关键词检索当前 milestone 内可能相关的其他 slug；只有用户明确提及历史版本时才扩大到其他 milestone。
4. 展示候选文档路径及关联原因。当前 slug 内候选默认全选，跨 slug 候选由用户选择。
5. **确认门禁**：等待用户确认 Bug 信息和关联范围。
6. 用户确认后，按 `references/bug-template.md` 创建 `<slug_dir>/Bug/BugN_<标题>.md`：
   - `N` 按已有 Bug 文档自增。
   - 关联需求使用相对 `.agent/story/<current_milestone>/` 的路径。
   - 状态由 `待确认` 更新为 `已确认`。

# Phase 2: 根因分析与分流

1. 探索相关代码并对照关联文档，区分：
   - 实现偏离设计；
   - 设计遗漏边界或依赖；
   - 接口、数据或跨模块交互问题。
2. 将证据、根因和影响范围写入 Bug 报告。
3. 输出根因摘要、拟修改文件和修复方案，判定修复路径：

### 小修

同时满足：

- 修改范围不超过 3 个函数；
- 不改变逻辑分支、数据结构、接口签名或 UE 元数据；
- 不影响需求文档定义的接口契约。

先展示根因和具体修改方案，**等待用户确认后**进入 Phase 3，禁止直接修改文件。

### 大修

满足任一项：

- 涉及逻辑分支、数据结构、接口签名或 UE 元数据；
- 跨模块影响；
- 修复方案与关联需求设计冲突。

说明判定理由并等待用户确认，然后调用 `/story-design` 更新设计，再调用 `/story-implement` 实现。对应 skill 完成后返回 Phase 4。

> 修复引入全新需求时，不作为 Bug 大修直接扩展；记录为衍生需求并引导 `/story-story` → `/story-design`。

# Phase 3: 小修实施

1. 将 Bug 状态更新为 `修复中`。
2. 按用户确认的方案修改代码，并进行与改动风险相称的验证。
3. 在 Bug 报告记录实际修改、验证方法和结果。
4. 若实施中发现需改变设计或接口契约，立即停止并转入大修路径。
5. 代码完成且验证通过后，将状态更新为 `已修复`。

# Phase 4: 验证与交付

1. 核对代码、Bug 报告和关联需求文档是否一致。
2. 影响需求边界或接口契约 → 更新关联需求文档；需要刷新总览时提示使用 `/story-consolidate`。
3. 需要审查时调用 `/story-review`；Review 的问题继续回到修复流程，直至阻断问题清零。
4. 验证完成后将状态更新为 `已验证`，输出：
   - Bug 报告路径；
   - 关联或更新的需求文档路径；
   - 修改/新增源文件及验证结果；
   - `✅ BugN <标题> 已验证关闭`。
5. 若本次根因或修复方式可跨需求复用，提示可调用 `/story-learn` 提炼到 library；仅在用户确认后沉淀。
