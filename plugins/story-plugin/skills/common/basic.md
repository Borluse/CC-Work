# 方案，需求设计规则
当与用户讨论方案或者设计细节时，请就这个方案或设计的每一个细节对我进行持续的深度追问，直到我们达成完全一致的理解。请遍历设计树的每一个分支，逐一梳理并解决各个决策之间的依赖关系。针对每一个问题，请附上你推荐的解答或建议。每次请只提一个问题。如果某个问题可以通过探索代码库来得出答案，请直接去探索代码库（而不需要向我提问）。

# 目录简介

文档都在工作目录的 `.agent`下
目录结构如下：
.agent
├── library
└── story
    └── 大需求
        ├── wiki 
        ├── archive
        ├── Review
        │   └── 需求1_代码Review.md
        ├── TDD_大需求.md
        ├── 需求1_需求描述.md
        ├── 总览.md
        └── 原始需求.md

- slug : 表示一个短语用来描述一组需求，例如`飞行射击怪`
- `.agent/story/<slug>`: 表示一组需求所在的目录
- slug 下 `archive` 目录为已经archive的需求，不需要访问，只用做存档
- slug 下 `review` 目录为review代码或设计的文档
- slug 下 `wiki` 目录为当前需求的wiki文档。用来供用户阅读，AI不需要参考

## slug 下文档种类
- `总览.md` 为当前需求的整合文档。通常为一个需求结束后整合成一个完整的文档。
- `原始需求` 为策划的原始需求文档，查看用来获取当前需求的设计，来自策划。
- `需求*_.md`为具体某个需求的设计文档，例如 `需求1_技能1.md`
- `*_代码review.md`为基于某个需求来review代码的文档，例如 `需求1_代码review.md`
- `*_需求review.md`为基于某个需求来review需求文档的文档，例如`需求1_需求review
- `TDD_*` 为相对原始需求的技术设计文档。

## 工作流

- 用户提供`原始需求`文档
- 从`原始需求` 和实际技术中，讨论出 `TDD_` 方案，`TDD` 本身不涉及具体的代码，只有一个大概的可行性的方案讨论
- 一套`原始需求` 可能含有若干需求点，例如10个技能。`TDD`中会承载这些讨论出的需求点
- `TDD`中的需求，经过design设计生成对应凯恩需求设计文档。每一个需求会有一个独立的文档
- 需求文档在生成代码后，可以通过review生成review文档
- 在结束后使用consolidate合并成总览文档
  
## 文档规则
- 需求标号总是为自增，例如，`需求1`, `需求2`
- 一个slug下总是只有一个`总览.md`，总是通过consolidate命令将单个需求文件合并到总览

## Slug命名规则
- 提炼 ≤5 词中文短语作为目录名（如 `怪物推挤`），向用户确认。
- 总是向用户询问当前slug

# 上下文获取
- 与项目有关的设计，代码，规则等，加载 `.agent/library/overall.md` 这个文件获取知识。
- 当需要设计C++代码，加载 `.agent/library/common/ue5-cpp-rule.md` 获取规范

# 文档先行规则
任何与需求文档描述不一致的代码变更，或用户要求修改内容，**必须先更新需求文档对应章节，再修改源代码**。
以下情况均视为设计偏差，需先更文档：
- 接口签名变更（参数增删、返回值类型变化、函数名变更）
- 结构体/类名重命名
- UCLASS/UPROPERTY/USTRUCT 等 UE 元数据变更（DisplayName、Category、meta 等）
- 逻辑流程与伪代码/流程图不一致（如新增校验步骤、分支变化）
- 新增或移除成员变量/配置项
- 碰撞通道、Debug 策略等实现细节与「注意事项」描述不符
- 修改涉及到多个文件，多个接口

规则：
1. 根据slug找到对应需求，也可能是总览
2. 在「变更记录」追加：`**<YYYY-MM-DD HH:mm>**：[实现] <变更简述>`
3. 给出简要的变更总结，供用户审查
