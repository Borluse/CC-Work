# 方案，需求设计规则
当与用户讨论方案或者设计细节时，请就这个方案或设计的每一个细节对我进行持续的深度追问，直到我们达成完全一致的理解。请遍历设计树的每一个分支，逐一梳理并解决各个决策之间的依赖关系。针对每一个问题，请附上你推荐的解答或建议。如果某个问题可以通过探索代码库来得出答案，请主动使用 ast-grep、rg 或 fd 等命令行工具直接去探索代码库检索相关逻辑，提取信息后再做决策。
提问题时，禁止使用`askuserquestion`工具 。

# 目录简介

文档都在**当前工作目录**的 `.agent`下
忽略文件：无需访问 wiki 和 archive 目录。
核心流转：读取原始需求 -> 讨论输出TDD -> 拆解为多个需求*_.md -> 结束后合并为总览.md。

例如当前的工作目录为 D:\Work
所有的文档获取和上下文加载，均默认以当前全局配置根目录（即 .agent 所在的工作目录）为基准构建相对路径。

目录结构如下：
```
D:\Work\.agent
├── library
└── story
    └── 2026-4-30_大需求
        ├── wiki 
        ├── archive
        ├── Review
        │   └── 需求1_代码Review.md
        ├── TDD_大需求.md
        ├── 需求1_需求描述.md
        ├── 总览.md
        └── 原始需求.md
```
 
## 文档规则
- 需求标号总是为自增，例如，`需求1`, `需求2`
- 一个slug下总是只有一个`总览.md`

## Slug命名规则
- 提炼 ≤5 词中文短语作为目录名（如 `怪物推挤`），向用户确认。
- 目录格式为 `日期_需求slug`，日期为生成该slug的时间，例如 `2026-4-30_怪物推挤`
- 在开启新任务或缺失 slug 上下文时，必须向用户确认当前的 slug 名称。

# 上下文获取
- 加载 `.agent/library/overall.md` 这个文件获取项目知识。
- 仅当任务明确涉及读取和写入代码块时，才加载 `.agent/library/common/ue5-cpp-rule.md` 获取代码规范。

# 文档先行规则
任何实质性的变更（包括但不限于逻辑分支、数据结构、接口签名、UE元数据等），必须先更新对应的需求文档及总览，再修改源代码。
修改后在文档末尾追加：<YYYY-MM-DD>：[类型] 变更简述（严禁大段记录）。
