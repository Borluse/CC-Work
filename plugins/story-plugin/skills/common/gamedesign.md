# 设计，实现代码时的准则

## 核心设计准则
- **不假设、不脑补**：信息缺失或不确定 → **必须**先提问，**禁止**替用户做决定。
- **最小化设计（YAGNI）**：每个设计须有明确当前需求支撑，**禁止**"以防万一"式过度设计。
- **调研工程**：根据指导文件，主动搜索工程目录（`.h`, `.cpp`, `.ini` 及测试地图），了解现有实现、配置逻辑及测试场景。

## 设计时，向自己询问如下问题，
- **网络与同步**：是否需要网络同步，断线重连是否有问题。
- **同步方式**：属性复制还是rpc？属性赋值能满足尽量用属性赋值。
- **复用**: 对象池参与下，功能复用是否有问题。考虑用UProperty，回对象池会用反射还原参数到CDO
- **原生优先**：是否有原生UE实现，或项目中已封装接口
- **异常处理**：模块可能产生的极端边界情况及降级策略。

# 输出规范：方案设计与说明
输出设计方案必须包含：
1. **实现思路与涉及功能**：简述核心逻辑，罗列需用到的引擎模块或现有代码基建。
2. **资产配置指南**：涉及资产配置（行为树、PhysicsControlAsset、AnimMontage、DataAsset、DataTable、GameplayAbility 等）→ **必须**提供具体配置步骤、关键参数名及推荐值，确保策划能按图索骥。
3. **调试与测试支持**：程序+策划双视角，提供测试手段。包括：CVar 控制台变量（开关/数值覆盖）、Cheat Manager 指令或可视化 Debug 绘制。

# 讨论与提问规范
与用户讨论方案/设计细节时，对每个细节持续深度追问，直到达成完全一致理解。遍历设计树每个分支，逐一梳理解决各决策依赖关系。每个问题附推荐解答/建议。若问题可通过探索代码库得答案 → 主动用 ast-grep、rg、fd 检索相关逻辑再做决策。
提问时禁止使用 `askuserquestion` 工具。

## 提问与选项编号规范
- 问题做分类
- 问题结构：
  - Q1.(Q+数字) 问题标题
  - 原因解释（原因/影响面/涉及面等）
  - A/B/C 可选项
  - 推荐选项及原因
  - 分隔符
