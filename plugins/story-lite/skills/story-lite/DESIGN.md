# Design 模式（文档即沟通媒介，含需求拆分）

前置：已完成主技能定位，并已读取主技能的约定、状态规则、提问规范与模板门禁。

入口：定位后的新正式需求，或路由命中 Design、拆分、TDD、大需求规划。

出口：设计确认后停在 `已确认`；用户明确要求实现或开工时转 `IMPLEMENT.md`；用户要求设计 Review 时转 `REVIEW.md`。

## 1. 范围与拆分

- 若已有多点需求：先确认本次要新增或修改的目标需求点。
- 若规模大（工作流规则、接口、数据结构变更，或跨多文件、超出单文件局部；不确定则从严）：才新增需求点。须用户确认。不得自行拆分。续用追加同样。
- 若单点中途规模扩大：暂停并确认是否拆分。已有总览则直接扩展；既有无总览单点按本模式第 3 步迁移状态承载。
- 跨 milestone 续用 slug 时，新工作在当前 `<ms_dir>` 新建需求点；拆分确认后，询问是否改变已有需求点的契约、行为或关键决策。若改变，列出候选旧点并确认回写范围。
- 本步只确认拆分，不落清单。定位阶段按本规则确认。

## 2. 检索设计上下文

- 设计前读 `<cwd>/.agent/library/overall.md`。若不存在：跳过。本会话读一次。按主题找子文档。
- 按主技能「检索既有设计」检索相关设计（含当前 slug 其他需求点）并深读。已读入的 `index.yaml` 复用，按当前描述重新匹配。当前 slug 目标文档按本模式第 3、4 步读取，不计入深读限额。
- library 与既有设计仅线索。事实以代码为准。

## 3. 总览规划

仅当：新建正式需求，本次确认新增或拆分需求点，或用户触发拆分、TDD、大需求规划。

1. 按主技能「总览读取策略」分层读取：先读主题根 `原始需求.md`、`index.yaml` 与总览中和新点相关的目标、技术约束、系统盘点、跨需求依赖及未闭合问题章节；再只读各需求点文档的头部方案节定位归属与依赖；仅对与新点有依赖、复用或回写关系的点深读正文。与新点无交互的点靠账本条目即可，不读正文；历史变更记录默认跳过。保留既有内容。明确复用、扩展与继承关系。
2. 用 `fd`、`rg` 盘点相关系统、模块与基类。
3. 分类为怪物类或通用系统：
   - 怪物类：关注玩法、技能、制作方案、资源与性能约束。
   - 通用系统：关注核心机制、系统关系、配置方向与关键约束。
4. 总览规划为独立确认范围。按主技能提问规范补齐该范围的决策后，一次性展示：整体目标与技术约束、相关系统盘点、简明需求点清单、跨需求依赖图、未闭合问题和总览结构。
5. 若用户确认：创建或更新主题根 `总览.md`。每个新增需求点先将 `requirement` 加一并向 `items` 追加：`id` 为新编号，`title` 为标题，`milestone` 为 `current`，`status` 为 `待设计`。再以该编号更新总览清单中的一行；只有新点影响跨需求契约、依赖、系统关系或未闭合风险时，才同步更新对应总览章节。详细方案写入需求点文档，不在总览复制；其余需求点条目保持不变。
6. 若既有无总览单点进入总览规划：先按总览或设计文档补全该 id 的 `items` 条目（`status`；有则写入 `file` 与 Review 路径，`keywords` 按约定从设计抽出），再将影响跨需求契约、依赖或风险的决策摘要迁入总览；详细设计保留在需求点文档，不删除其唯一承载。随后仅新增或受影响需求点进入详细设计。不生成独立 TDD 文档。

## 4. 目标需求点详细设计

- 单点需求：直接进入。
- 已有多点且已确认目标：直接进入。
- 刚完成总览规划：仅新增或受影响的需求点进入。
- 每个目标需求点按主技能提问规范独立确认。确认前不写设计文档。至少覆盖：逻辑落在哪个模块或类、表现端如何拿到服务端数据、盘点中的相近系统如何复用、扩展或只参考。缺任一项则前沿未空。

## 5. 落盘设计

按条目的 `milestone` 写入 `<ms_dir>/需求N_标题.md`，使用已占编号且不再增加 `requirement`；把 `file` 写成相对 `<slug_dir>` 的实际路径，状态写 `设计中`，并按约定从该设计文档重写 `keywords`。

- 若已有总览：同步总览中的目标需求点简明清单行；只有方案改变跨需求契约、依赖、系统关系或风险时，才更新对应总览章节。详细方案写入需求点文档，不在总览新增完整需求点方案节。
- 若为既有无总览单点：在设计文档中写关键决策。
- 若已确认回写旧点：按旧条目的 `milestone` 定位设计文档，只更新被新点改变的契约、行为或关键决策，旧点状态不变；旧点尚无 `items` 条目时先补这一条，再把新条目的 `continues` 加入旧点 id、旧点的 `continued_by` 加入新点 id。被回写的旧点若改了设计，按约定处理其 `keywords`。

## 6. 文档确认循环

展示 → 用户反馈 → 改文档 → 再展示，直至确认。

1. 展示设计时一并列出该条 `keywords`，用户可以改。改设计时按约定重抽并展示与现有的差异，确认后才覆盖。
2. 用户确认后，按状态规则写 `已确认`。
3. 用户可在 `设计中` 直接要求设计 Review，转 `REVIEW.md`，不必先确认。
4. 设计 Review 需改方案时：回到本模式第 5 步更新文档，再复查。

## 7. 出口门禁

设计确认后停在 `已确认`。

- 只有当用户原话已要求做功能，或之后说了「实现 / 开工」，才转 `IMPLEMENT.md`。
- 仅说「确认 / ok / 看起来可以」只确认文档，不等于开工。
- 设计尚未确认时，禁止改代码。跳过详细设计的小改见 `IMPLEMENT.md` 门禁。
