# 定位

轻量版需求工作流：正式需求走「需求整理 → 设计（含需求拆分，文档沟通）→ 实现（文档同步）→ Review（按需）→ 整合/总结（按需）」；quick 任务走「需求文档 → 确认 → 实现」。核心目的：**让 agent 维护文档，而不是只写代码或只做设计**。

**使用前提**：本技能只在用户显式点名（@story-lite / plugin://story-lite / 说『用 story-lite』）时启用，不自动命中。点名即激活：第一动作执行「1 定位」并向用户展示定位结论，未完成前不得进入内容讨论或改动任何文件。豁免仅限无任何文件产出、无改动的纯信息问答；凡涉及新增/修改文件的任务一律走工作流——包括对本技能/插件本身的修改（元任务不豁免，续入相关 story）。

# 文档结构（沿用 story 约定）

```
.agent/
├── milestones.yaml                  # 当前 milestone（示例与说明见下文）
└── story/<milestone>/
    ├── Archive/                     # 若有则忽略，不要碰触
    ├── quick/                       # quick 模式：简单独立任务
    │   └── YYYY-MM-DD_任务短语.md   # 需求文档（不 review、不总结）
    └── <YYYY-MM-DD_slug>/
        ├── 原始需求.md              # 需求入口
        ├── 需求N_标题.md            # 每个需求点一个设计文档（多个）
        ├── 总览.md                  # 需求点清单（多需求点）+ 增量维护（单点需求不建）
        └── review/                  # 审查文档
            ├── 需求N_标题_设计review.md
            └── 需求N_标题_代码review.md
```

# 约定

- `<cwd>`：包含 `.agent` 的当前项目根目录；多根工作区或无法唯一确定时先与用户确认
- slug：`YYYY-MM-DD_需求slug`，slug 为 ≤5 词中文短语（如 `html文件浏览器`），创建前与用户确认；目录内所有日期统一 `YYYY-MM-DD`
- 命名：
  - 设计文档：`需求N_需求标题.md`，编号按需求点清单从 1 开始；单点需求固定 `需求1_需求标题.md`；quick 任务不产设计文档
  - quick 文档：`YYYY-MM-DD_任务短语.md`；review 报告：`需求N_标题_设计review.md` / `需求N_标题_代码review.md`
- 变更记录：`- <YYYY-MM-DD HH:mm>：初始创建/修改`，适用于原始需求、设计文档、总览；quick 文档和 review 报告除外；职责分工：原始需求只记需求追加，设计文档记设计变更，总览记多需求点的聚合变更；状态转换与小改动更新状态承载文档
- 文档先行：实质性变更（逻辑、接口、数据结构）先更新文档再改代码；文档与代码冲突时以代码为准并标注
- 状态承载：多需求点的状态只写 `总览.md`，单点需求的状态只写对应设计文档；单点设计文档创建前隐式视为「待设计」，不另行落盘；quick 文档使用自由文本的「结果/状态」，不使用正式需求枚举
- 正式需求状态枚举：待设计（未开始）/ 设计中（未确认）/ 已确认（等待实现）/ 实现中 / Review 中 / 已完成（实现完未代码 review 或无需 review）/ 已Review（代码 review 问题清零或用户确认结束）/ 阻塞（被外部条件阻塞）
- 状态转换：设计方案首次落盘 → 设计中；设计文档确认 → 已确认；开始实现 → 实现中；实现结束 → 已完成；开始 review → Review 中；代码 review 结束 → 已Review；设计 review 结束 → 设计中或已确认；外部阻塞 → 阻塞（变更记录写明原因与前状态），解除后恢复前状态
- 提问规范仅用于需求与设计中的未决策事项

# Milestone 配置（.agent/milestones.yaml）

```yaml
current: 切片1
milestones:
  切片1:
    created: 2026-05-20
  MS10:
    created: 2026-04-15
```

- `current` 指向当前活跃 milestone，所有 slug 操作默认在该 milestone 目录下执行
- 文件不存在时，展示上述模板并确认当前 milestone；用户确认后由 agent 创建，再重新执行定位

# 提问规范（需求与设计澄清）

对影响需求、验收或实现路径的未决策事项坚持访谈直至达成共识。将决策梳理为设计树：每一个决策都会衍生出依附于它的后续决策。已明确的用户需求、可查证事实和纯执行步骤不进入访谈。

- **按轮次处理前沿**：待处理前沿 = 所有前提已确定、可直接提出、无需猜测尚未知晓答案的决策。每轮集中提出整个待处理前沿；用户作答后重算前沿，进入下一轮。若某题答案依赖本轮尚未解决的另一题，则属后续轮次，不得放入本轮。
- **问题格式**（每题）：

❓ **Q1** - **<标题>**: <正文：原因；可多段>

A. …
B. …
C. …

➡️ <推荐答案及原因>

  有可选项时每个选项独占一行；无离散选项时可省略 A/B/C。每轮题号从 Q1 起编。
- **决策权在用户**：每题必须给出推荐答案；推荐是引导而非决定；禁止脑补未决事实、禁止替用户拍板。
- **查证优先（事实由 agent 找）**：可自查的环境事实（文件系统、代码等）由主 agent 直接查（rg/读文件等），不向用户索要；范围大或需并行探索时派子代理。正在进行的探索视为未定前提——仅其下游问题等待子代理报告，其余前沿照常提问，不得因此停滞整轮。
- **结束条件**：前沿为空且用户确认已达成共识时，提问会话结束（设计树分支均已遍历）；此前不得写设计文档、总览或代码。
- **文档纪律**：用户已经明确表达的原始需求或 quick 需求可先整理为草稿并展示确认；未确认的设计细节不写入设计文档或总览，全部确认后一次性落盘，再走文档确认循环。

# 工作流程

## 模式路由（触发词 → 模式）

以下路由均在 1 定位完成后生效；每次点名激活本技能时始终先执行 1，再进入目标模式。

| 用户触发 | 命中模式 |
|----------|----------|
| 描述新需求 / 「做 XX」 | 1 定位与需求整理 |
| 简单独立任务 / 无规则与接口变更的中小任务（加日志、debug、小改动等） | 2 Quick（先判断是否符合条件，再与用户确认） |
| 「拆分」/ 多需求点大需求 | 3 Design（先判断规模、与用户确认拆分） |
| 「设计」/「写设计文档」 | 3 Design |
| 「实现」/「开工」 | 4 实现与同步维护 |
| 正式需求的「review」/「审查」 | 5 Review（先确认设计或代码） |
| 「整合」/「生成总览」/ 里程碑收尾 / 「总结」 | 6 整合与总结 |

## 1. 定位与需求整理

- 点名本技能后的第一动作；定位结论（milestone + 工作目录）先向用户展示，未完成本步不得进入内容讨论或改动任何文件
- 读取 `<cwd>/.agent/milestones.yaml` 获取当前 milestone；不存在则按「Milestone 配置」创建后重新执行定位
- 在 `.agent/story/<milestone>/` 下查找同主题正式需求 slug（忽略 `Archive/` 与 `quick/`），并判断任务适合 Quick 还是正式需求；先向用户确认分支，再创建或修改文档
- **Quick 分支**：输出 `<milestone>` 与 `<quick_dir>`，转 2 Quick；不创建 slug，不写 `原始需求.md`
- **正式需求分支**：已有同主题 slug 时与用户确认续用并追加需求点；未命中时与用户确认新 slug；输出 `<milestone>` 与 `<slug_dir>`
- 正式需求是否新增需求点（拆分）与续用追加需求点，默认在定位阶段按 3 Design 第 1 步判定并由用户确认；单点需求不拆分；中途发现规模扩大时按 3 Design 的例外规则处理
- 仅正式需求清理用户已经明确表达的内容：新 slug 写入 `<slug_dir>/原始需求.md` 并记「初始创建」，续用 slug 追加需求与变更记录；随后在同一会话进入 3 Design，无需用户再次触发；未决策的设计细节留待 Design 澄清

**模板：**

```markdown
# 原始需求：<slug 描述>
- <YYYY-MM-DD HH:mm>：初始创建
（后续变更记录继续追加在标题下）
## 需求背景
## 需求描述
## 验收标准
```

## 2. Quick 模式（简单独立任务）

- 适用：无独立 slug 的简单独立任务，或影响面可评估、无工作流规则/接口/数据结构变更的中小任务（如加日志、debug、小改动）；路由时与用户确认；中途发现影响面超出范围，暂停并提议转正式需求流程
- 不建原始需求 / 设计文档；**不做 review、不纳入总结**
- 流程：写 quick 需求草稿 → 展示给用户确认 → 实现 → 更新改动文件与结果/状态；确认前不得改代码，多轮修改持续更新该文档
- 用户要求 review、整合或总结 Quick 任务时，说明 Quick 约束并询问是否转正式需求；用户确认转换后重新执行 1 定位

**模板：**

```markdown
# Quick：<任务短语>
- 日期：YYYY-MM-DD
- 需求：一句话简介
## 方案
## 改动文件
## 结果/状态
```

## 3. Design（文档即沟通媒介，含需求拆分）

1. **需求拆分（仅大需求，需用户确认）**：是否新增需求点通常只在调用本技能（定位阶段）时判断；仅当判定当前需求点规模较大（涉及工作流规则/接口/数据结构变更，或跨多文件、影响面超出单文件局部改动；不确定时默认从严）才启用新的需求点，且必须先与用户确认，不得自行拆分；续用 slug 追加需求点同样按此判定并需用户确认。中途发现需求规模扩大时，暂停并再次提出新增需求点，等用户确认。此步只确认拆分结果，不落清单；单点需求不建立总览
2. **提问澄清（不落设计）**：按「提问规范」按轮次提出待处理前沿并迭代，直至前沿为空且用户确认共识；此阶段不写设计文档或总览
3. **落盘设计**：全部细节确认后，将方案写入 `<slug_dir>/需求N_标题.md` 并将状态置为「设计中」；多需求点同时创建或更新 `总览.md` 的需求点清单，单点需求将状态与关键决策写在设计文档
4. **文档确认循环**：文档最新版即当前方案，每次更新后展示给用户；反馈 → 改文档 → 再展示，循环直到确认；确认后将状态置为「已确认」。设计 review 返回「设计中」时也从本步重新确认
5. **进入实现**：用户确认前禁止修改代码文件；**较大修改必须等待用户审阅确认设计文档后才可落地**，不得以「直接实现 / 跳过设计」绕过；小修改在用户明确说「直接实现 / 跳过设计」时可跳过详细提问与确认循环，但仍须写最小设计记录并将状态置为「已确认」

**模板：**

```markdown
# 需求N：<标题>
- 状态：<枚举值>（仅单点需求；多需求点省略本行并以总览为准）
- Review：<链接>（仅单点需求且已有报告时）
## 需求简介
一句话。
## 功能说明
策划目标 + 技术行为。
## 设计细节
图文并茂（mermaid），代码用伪代码表达；关注网络同步、原生 API 优先、复用与异常处理。
## 变更记录
- <YYYY-MM-DD HH:mm>：初始创建/修改
```

## 4. 实现与同步维护（核心）

**入口门禁：**

- 正式需求：必须已有 `原始需求.md` 与对应设计文档，且状态为「已确认」；较大修改的设计文档必须经用户审阅确认。小修改只有在用户明确要求跳过详细设计、最小设计记录已写入且状态已置为「已确认」时才能进入实现
- Quick：必须已有经用户确认的 quick 文档
- 条件不满足时返回 2 Quick 或 3 Design，不得改代码

**同步检查点：**开始实现、出现新的实质性设计决策、进入或解除阻塞、实现完成时，同步更新对应文档；连续的小型代码修改在下一检查点合并记录，不逐次写文档。

- 开始实现：正式需求状态改为「实现中」；Quick 的结果/状态改为「实现中」
- 实现过程：功能说明与实际行为保持一致；接口、数据结构或工作流规则变更必须先更新设计文档，再改代码
- 状态与链接：多需求点更新总览中的状态、关键决策和文档链接；单点需求更新设计文档；Quick 更新自身文档
- 实现完成：记录改动文件与结果；正式需求状态改为「已完成」，Quick 的结果/状态改为「已完成」
- 变更记录：正式需求按「约定」追加 `- <YYYY-MM-DD HH:mm>：修改说明`

**铁律**：正式需求缺少原始需求或设计文档、Quick 缺少 quick 文档时不得开工；检查点文档未同步 = 工作未完成；实事求是不脑补。

**总览模板：**

```markdown
# 总览：<slug 描述>
## 需求点清单（多需求点）
| 编号 | 名称 | 目标 | 功能范围 | 方案思路 | 依赖 |
|------|------|------|----------|----------|------|
| 1 | … | … | … | … | - |
（依赖复杂时附 mermaid 依赖图）
## 需求点 N：<标题>
- 状态：<枚举值>
- 关键决策：…
- 设计文档：<链接>
- Review：<链接>
## 变更记录
- <YYYY-MM-DD HH:mm>：说明
```

## 5. Review 模式（输出审查文档，subagent 执行）

1. 确认当前对象是正式需求；Quick 不进入 Review，按 2 Quick 的转换规则处理
2. 询问 review 设计还是 review 代码；仅审查本次需求相关内容，严禁超纲。设计 review 须已有对应设计文档；代码 review 须当前状态为「已完成」或「已Review」（复查）；不满足时返回 3 Design 或 4 实现。满足门禁后将状态改为「Review 中」
3. **优先委托 subagent 执行审查**：创建通用审查子代理；环境不支持或子代理未能有效执行（未产出可用报告）时，主 agent 自行审查，报告末尾注明「主 agent 执行」
4. 向子代理清晰传递：审查类型（设计/代码）、`<slug_dir>` 下相关文档路径、需求上下文、涉及文件路径
5. 子代理落盘报告到 `<slug_dir>/review/`：命名见「约定」；同需求报告已存在 → 先读取，在保留历史修复记录的基础上更新，禁止盲目覆盖
6. 主 agent 展示报告路径、摘要与问题清单，询问「哪些问题需要现在修复」；修复后再次委托复查并原地更新报告，直至问题清零或用户确认结束
7. 结束时更新状态承载文档和报告链接：设计 review 仍需修改 →「设计中」，设计 review 通过或用户确认方案 →「已确认」；代码 review 问题清零或用户确认结束 →「已Review」。多需求点更新总览，单点需求更新设计文档；保留未修问题与全部历史修复记录

**报告模板：**

```markdown
# 需求N_标题_<设计或代码>review
- 日期：YYYY-MM-DD
- 关联需求：需求N_标题
## 问题清单
| 编号 | 问题 | 原因 | 影响面 | 建议 |
|------|------|------|--------|------|
## 修复记录
（历史修复记录保留，复查后原地更新，禁止盲目覆盖）
```

## 6. 整合与总结

触发：用户说「整合 / 生成总览」或里程碑收尾（整合）；用户说「总结」（总结）。

- **范围**：「整合 / 生成总览 / 总结」默认处理当前正式需求 slug；「里程碑收尾」处理当前 milestone 下除 `Archive/`、`quick/` 外的全部正式需求 slug，各 slug 独立整合，不创建额外的里程碑总览
- **多需求点整合**：读总览（含需求点清单）+ 全部设计文档 + 实际代码，刷新 `总览.md`
- **单点需求整合**：读原始需求 + 设计文档 + 实际代码，刷新设计文档，不创建 `总览.md`
- **共同规则**：以代码为准，文档与代码不一致处标注；去重合并，代码中不存在的功能不写入；保留重要设计决策（「为什么这样做」）；在对话中输出差异报告，用户要求时再将差异章节写入状态承载文档
- **总结**：多需求点读总览 + 各设计文档 + review 报告；单点需求读原始需求 + 设计文档 + review 报告；按需求分组输出完成项 / 进行中 / 阻塞 / 决策与经验
- **里程碑收尾结束条件**：全部正式需求 slug 处理完成后，在对话中输出里程碑级摘要；用户确认收尾即结束，不修改 `milestones.yaml`，除非用户明确要求切换 current
- 总览 = 多需求点聚合视图（当前状态），设计文档保留过程细节，review 文档记录问题；Quick 不进入整合或总结，按 2 Quick 的转换规则处理
