# 定位

轻量版需求工作流：正式需求走「需求整理 → 设计（含需求拆分，文档沟通）→ 实现（文档同步）→ Review（按需）→ 整合/总结（按需）」；quick 任务走「需求文档 → 实现」。核心目的：**让 agent 维护文档，而不是只写代码或只做设计**。

**使用前提**：本技能只在用户显式点名（@story-lite / plugin://story-lite / 说『用 story-lite』）时启用，不自动命中。点名即激活：第一动作执行「1 定位」并向用户展示定位结论，未完成前不得进入内容讨论或改动任何文件。豁免仅限无任何文件产出、无改动的纯信息问答；凡涉及新增/修改文件的任务一律走工作流——包括对本技能/插件本身的修改（元任务不豁免，续入相关 story）。

# 文档结构（沿用 story 约定）

```
.agent/
├── milestones.yaml                  # 当前 milestone（schema 见下文）
└── story/<milestone>/
    ├── Archive/                     # 若有则忽略，不要碰触
    ├── quick/                       # quick 模式：简单独立任务
    │   └── YYYY-MM-DD_任务短语.md   # 需求文档（不 review、不总结）
    └── <YYYY-MM-DD_slug>/
        ├── 原始需求.md              # 需求入口
        ├── 需求N_标题.md            # 每个需求点一个设计文档（多个）
        ├── 总览.md                  # 需求点清单（多需求点）+ 增量维护（单点需求不建）
        └── review/                  # 审查文档
            ├── 需求N_标题_设计review.md
            └── 需求N_标题_代码review.md
```

# 约定

- slug：`YYYY-MM-DD_需求slug`，slug 为 ≤5 词中文短语（如 `html文件浏览器`），创建前与用户确认；目录内所有日期统一 `YYYY-MM-DD`
- 命名：
  - 设计文档：`需求N_需求标题.md`，编号按需求点清单从 1 开始；单点需求固定 `需求1_需求标题.md`；quick 任务不产设计文档
  - quick 文档：`YYYY-MM-DD_任务短语.md`；review 报告：`需求N_标题_设计review.md` / `需求N_标题_代码review.md`
- 变更记录：`- <YYYY-MM-DD HH:mm>：初始创建/修改`，适用于原始需求、设计文档、总览；quick 文档和 review 报告除外；职责分工：原始需求只记需求追加，设计文档记设计变更，总览记里程碑级变更与状态转换，小改动只更新总览
- 文档先行：实质性变更（逻辑、接口、数据结构）先更新文档再改代码；文档与代码冲突时以代码为准并标注
- 总览状态枚举（每个需求点「状态」只允许取这些值）：待设计（未开始）/ 设计中（未确认）/ 已确认（等待实现）/ 实现中 / Review 中 / 已完成（实现完未 review 或无需 review）/ 已Review（问题清零或用户确认结束）/ 阻塞（被外部条件阻塞）
- 提问规范见下节，适用于所有环节

# Milestone 配置（.agent/milestones.yaml）

```yaml
current: 切片1
milestones:
  切片1:
    created: 2026-05-20
  MS10:
    created: 2026-04-15
```

- `current` 指向当前活跃 milestone，所有 slug 操作默认在该 milestone 目录下执行
- 文件不存在时，向用户展示上述模板并请其创建

# 提问规范（所有环节适用）

- **批量提问**：先遍历设计树、按依赖顺序梳理全部决策点，然后一次性提出当前所有未决问题（Q 编号 + 四要素），不逐个提问、不调单题问答工具；用户一次性答复后若产生新问题，下一轮继续批量提出，迭代直至完全一致
- **不预设答案**：出现疑问或不确定处一律提问，禁止脑补、禁止替用户做决定；「推荐选项」是引导而非决定，最终由用户确认
- **查证优先**：问题可通过探索代码库得答案 → 先用 rg 等检索相关逻辑，再做决策或提问
- **问题四要素**：标题、原因、可选项、推荐选项及其原因
- **选项单独成行**：每个可选项独占一行（A. … / B. … / C. …），推荐选项及原因单独一行，禁止与其他选项挤在同一行
- **文档纪律**：细节全部确认前不落任何文档（原始需求、设计文档、总览等）；全部确认后一次性落盘，再走文档确认循环
# 工作流程

## 模式路由（触发词 → 模式）

| 用户触发 | 命中模式 |
|----------|----------|
| 描述新需求 / 「做 XX」 | 1 定位与需求整理 |
| 简单独立任务 / 无规则与接口变更的中小任务（加日志、debug、小改动等） | 2 Quick（先判断是否符合条件，再与用户确认） |
| 「拆分」/ 多需求点大需求 | 3 Design（先判断规模、与用户确认拆分后再落清单） |
| 「设计」/「写设计文档」 | 3 Design |
| 「实现」/「开工」 | 4 实现与同步维护 |
| 「review」/「审查」 | 5 Review（先确认设计或代码） |
| 「整合」/「生成总览」/ 里程碑收尾 / 「总结」 | 6 整合与总结 |

## 1. 定位与需求整理

- 点名本技能后的第一动作；定位结论（milestone + 工作目录）先向用户展示，未完成本步不得进入内容讨论或改动任何文件
- 已存在同主题 slug → 续用并追加需求点（按 3 Design 第 1 步判定并需用户确认），不新建、不裸改文件
- 读取 `<cwd>/.agent/milestones.yaml` 获取当前 milestone；不存在则提示用户按上文模板创建
- 在 `.agent/story/<milestone>/` 下定位已有 slug；未命中则与用户确认后新建
- 是否新增需求点（拆分）与续用追加需求点：仅在定位阶段判断，判定标准与用户确认要求见 3 Design 第 1 步；单点需求不拆分
- 简单独立任务 → 转 2 Quick（与用户确认）
- 输出 `<milestone>` 与 `<slug_dir>`（正式需求）或 `<quick_dir>`（quick 任务）
- 清理用户需求、去除无用内容，写入 `<slug_dir>/原始需求.md` 并追加「初始创建」变更记录

**模板：**

```markdown
# 原始需求：<slug 描述>
- <YYYY-MM-DD HH:mm>：初始创建
（后续变更记录继续追加在标题下）
## 需求背景
## 需求描述
## 验收标准
```

## 2. Quick 模式（简单独立任务）

- 适用：无独立 slug 的简单独立任务，或影响面可评估、无工作流规则/接口/数据结构变更的中小任务（如加日志、debug、小改动）；路由时与用户确认；中途发现影响面超出范围，暂停并提议转正式需求流程
- 不建原始需求 / 设计文档；**不做 review、不纳入总结**
- 流程：写需求文档 → 展示给用户确认 → 实现 → 更新文档（改动文件、结果/状态）；多轮修改持续更新该文档

**模板：**

```markdown
# Quick：<任务短语>
- 日期：YYYY-MM-DD
- 需求：一句话简介
## 方案
## 改动文件
## 结果/状态
```

## 3. Design（文档即沟通媒介，含需求拆分）

1. **需求拆分（仅大需求，需用户确认）**：是否新增需求点通常只在调用本技能（定位阶段）时判断；仅当判定当前需求点规模较大（涉及工作流规则/接口/数据结构变更，或跨多文件、影响面超出单文件局部改动；不确定时默认从严）才启用新的需求点，且必须先与用户确认，不得自行拆分；续用 slug 追加需求点同样按此判定并需用户确认。中途发现需求规模扩大时，暂停并再次提出新增需求点，等用户确认。确认拆分后，先在 `<slug_dir>/总览.md` 落「需求点清单」（编号从 1 开始，方案思路可随设计确认补全）；单点需求跳过此步，不建立总览，状态与关键决策维护在设计文档（见模板）
2. **提问澄清（不落盘）**：按「提问规范」批量提出全部未决问题并迭代，直到与用户完全一致；此阶段不写任何文档
3. **落盘设计文档**：全部细节确认后，将方案写入 `<slug_dir>/需求N_标题.md`
4. **文档确认循环**：文档最新版即当前方案，每次更新后展示给用户；反馈 → 改文档 → 再展示，循环直到确认
5. **进入实现**：用户确认前禁止修改代码文件；**较大修改必须等待用户审查完设计文档后才可落地**，不得以「直接实现 / 跳过设计」绕过；小修改在用户明确说「直接实现 / 跳过设计」时可跳过提问澄清与确认循环，以最小设计记录后进入实现

**模板：**

```markdown
# 需求N：<标题>
- 状态：<枚举值>（单点需求维护于此；多需求点以总览为准）
## 需求简介
一句话。
## 功能说明
策划目标 + 技术行为。
## 设计细节
图文并茂（mermaid），代码用伪代码表达；关注网络同步、原生 API 优先、复用与异常处理。
## 变更记录
- <YYYY-MM-DD HH:mm>：初始创建/修改
```

## 4. 实现与同步维护（核心）

**较大修改**：设计文档经用户审查确认前，禁止修改任何代码文件。

实现代码时，每完成一项实质进展（一次修改、一个决策、解决一个问题），同步更新 `<slug_dir>` 下相关文档：

- 功能说明：与实际行为保持一致
- 变更记录：追加 `- <YYYY-MM-DD HH:mm>：修改说明`（按「约定」职责分工更新对应文档）
- 接口/数据结构变更：必须先更新设计文档，再改代码
- 总览增量维护：每个需求点有进展（设计确认/实现/Review）即更新对应章节：状态、关键决策、指向设计文档与 review 文档的链接

**铁律**：开工前无对应需求文档（原始需求 / quick 文档）不得改动文件；代码改了文档没更新 = 工作未完成；实事求是不脑补。

**总览模板：**

```markdown
# 总览：<slug 描述>
## 需求点清单（多需求点）
| 编号 | 名称 | 目标 | 功能范围 | 方案思路 | 依赖 |
|------|------|------|----------|----------|------|
| 1 | … | … | … | … | - |
（依赖复杂时附 mermaid 依赖图）
## 需求点 N：<标题>
- 状态：<枚举值>
- 关键决策：…
- 设计文档：<链接>
- Review：<链接>
## 变更记录
- <YYYY-MM-DD HH:mm>：说明
```

## 5. Review 模式（输出审查文档，subagent 执行）

1. 询问 review 设计还是 review 代码；仅审查本次需求相关内容，严禁超纲
2. **优先委托 subagent 执行审查**：创建通用审查子代理；环境不支持或子代理未能有效执行（未产出可用报告）时，主 agent 自行审查，报告末尾注明「主 agent 执行」
3. 向子代理清晰传递：审查类型（设计/代码）、`<slug_dir>` 下相关文档路径、需求上下文、涉及文件路径
4. 子代理落盘报告到 `<slug_dir>/review/`：命名见「约定」；同需求报告已存在 → 先读取，在保留历史修复记录的基础上更新，禁止盲目覆盖
5. 主 agent 收到落盘结果后，展示报告路径、摘要与问题清单，询问「哪些问题需要现在修复」；修复后再次委托复查并原地更新报告，直至问题清零；用户确认不修时，问题保留在报告中，需求点状态记为「已Review」

**报告模板：**

```markdown
# 需求N_标题_设计review / 需求N_标题_代码review
- 日期：YYYY-MM-DD
- 关联需求：需求N_标题
## 问题清单
| 编号 | 问题 | 原因 | 影响面 | 建议 |
|------|------|------|--------|------|
## 修复记录
（历史修复记录保留，复查后原地更新，禁止盲目覆盖）
```

## 6. 整合与总结

触发：用户说「整合 / 生成总览」或里程碑收尾（整合）；用户说「总结」（总结）。

- **整合**：读总览（含需求点清单）+ 全部设计文档 + 实际代码，刷新 `总览.md`。以代码为准，文档与代码不一致处标注；去重合并，代码中不存在的功能不写入；保留重要设计决策（「为什么这样做」）；在对话中输出差异报告（不一致处清单），供用户确认，用户要求时可将差异章节写入 `总览.md`
- **总结**：读总览 + 各设计文档（含变更记录）+ review 报告，按需求分组输出：完成项 / 进行中 / 阻塞 / 决策与经验；单点需求或总览缺失时直接读原始需求 + 设计文档 + review 报告
- 总览 = 聚合视图（当前状态），设计文档保留过程细节，review 文档记录问题；quick 任务不纳入总结
