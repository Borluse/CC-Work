# 定位

轻量版需求工作流：正式需求走「定位 → 需求整理 → TDD（可选）→ 设计（文档沟通）→ 实现（文档同步）→ Review（按需）→ 整合（按需）→ 总结（按需）」；quick 任务走轻量分支「需求文档 → 实现」。核心目的：**让 agent 维护文档，而不是只写代码或只做设计**。

**使用前提**：本技能只在用户显式点名时启用，不自动命中；纯问答、与需求工作流无关的一次性讨论不适用。

# 文档结构（沿用 story 约定）

```
.agent/
├── milestones.yaml                  # 当前 milestone（schema 见下文）
└── story/<milestone>/
    ├── Archive/                     # 若有则忽略，不要碰触
    ├── quick/                       # quick 模式：简单独立任务
    │   └── YYYY-MM-DD_任务短语.md   # 需求文档（不 review、不总结）
    └── <YYYY-MM-DD_slug>/
        ├── 原始需求.md              # 需求入口
        ├── TDD.md                   # 可选：大需求拆分（需求点清单与依赖）
        ├── 需求N_标题.md            # 每个需求点一个设计文档（多个）
        ├── 总览.md                  # 首个需求点设计确认后建立，增量维护 + 按需整合
        └── review/                  # 审查文档
            ├── 需求N_标题_设计review.md
            └── 需求N_标题_代码review.md
```

## 约定

- slug：`YYYY-MM-DD_需求slug`，slug 为 ≤5 词中文短语（如 `html文件浏览器`），创建前与用户确认；目录内所有日期统一 `YYYY-MM-DD`
- 设计文档命名：正式需求 `需求N_需求标题.md`；单点需求（无 TDD）固定为 `需求1_需求标题.md`；quick 任务不产设计文档，只产需求文档（见 Quick 模式）
- 变更记录：`- <YYYY-MM-DD HH:mm>：初始创建/修改`，适用于所有正式文档（原始需求、TDD、设计文档、总览）；quick 文档和 review 报告除外
- 文档先行：实质性变更（逻辑、接口、数据结构）先更新文档再改代码；文档与代码冲突时以代码为准并标注
- 提问规范：见「设计阶段提问规范」章节，所有环节的提问均适用

# 设计阶段提问规范

与用户讨论方案/设计细节时，遵循以下规范：

## 核心行为

- **批量提问**：先遍历设计树、按依赖顺序梳理全部决策点，然后一次性提出当前所有未决问题（Q 编号 + 四要素），不逐个提问；用户一次性答复后若产生新问题，下一轮继续批量提出，迭代直至达成完全一致理解。
- **不预设答案**：出现疑问或不确定处一律提问，禁止脑补、禁止替用户做决定。
- **查证优先**：问题可通过探索代码库得答案 → 先用 ast-grep、rg、fd 检索相关逻辑，再做决策或提问。
- **文档纪律**：细节全部确认前不落任何文档（原始需求、设计文档、总览等）；全部细节确认后一次性落盘，再走文档确认循环。

## 提问格式

- 编号：Q 递增编号（Q1、Q2…），方便批量问题的逐条对齐。
- 每个问题必须包含：标题、原因、可选项、推荐选项及其原因。
- 不强制问题分类与分隔符。
- 提问时禁止使用 `askuserquestion` 工具。

## 适用范围

- 本规范适用于所有环节（需求整理、Quick、TDD、Design、Review）中出现疑问/不确定的提问场景。

## Milestone 配置（.agent/milestones.yaml）

```yaml
current: 切片1
milestones:
  切片1:
    created: 2026-05-20
  MS10:
    created: 2026-04-15
```

- `current` 指向当前活跃 milestone，所有 slug 操作默认在该 milestone 目录下执行
- 文件不存在时，向用户展示上述模板并请其创建

# 工作流程

## 1. 定位

- 读取 `<cwd>/.agent/milestones.yaml` 获取当前 milestone；不存在则提示用户按上文模板创建
- 在 `.agent/story/<milestone>/` 下定位已有 slug；未命中则与用户确认后新建
- 简单独立任务（加日志、debug 等）→ 标记为 quick 模式，目标 `.agent/story/<milestone>/quick/`，与用户确认
- 输出 `<milestone>` 与 `<工作目录>`：正式需求为 `<slug_dir>`，quick 任务为 `<quick_dir>`

## 2. 需求整理

用户提供需求后，清理格式、去除无用内容，写入 `<slug_dir>/原始需求.md`，并追加变更记录「初始创建」。

## 3. Quick 模式（简单独立任务）

- 适用：无独立 slug 的简单独立任务（加日志、debug、小改动）
- 不建 `原始需求.md` / TDD / 设计文档；**不做 review、不纳入总结**
- 流程：
  1. 写需求文档 `<quick_dir>/YYYY-MM-DD_任务短语.md`（内容：日期、需求一句话简介、方案）
  2. 展示给用户确认
  3. 确认后实现
  4. 实现后更新文档：改动文件、结果/状态
- 多轮修改持续更新该文档

## 4. TDD 拆分（可选）

仅多需求点的大需求/Epic 需要：

- 输出 `TDD.md`：需求点清单（名称、目标、功能范围、方案思路）+ 依赖图
- 每个需求点对应一个 `需求N_标题.md`，编号从 1 开始，与 TDD 一致
- 单点需求无需 TDD，直接进入 Design

## 5. Design 模式：文档即沟通媒介

1. **提问澄清（不落盘）**：按「设计阶段提问规范」批量提出全部未决问题并迭代，直到与用户完全一致；此阶段不写任何文档。
2. **落盘设计文档**：全部细节确认后，将方案写入 `<slug_dir>/需求N_标题.md`，模板：
  - **需求简介**：一句话
  - **功能说明**：策划目标 + 技术行为
  - **设计细节**：图文并茂（mermaid），代码用伪代码表达；关注网络同步、原生 API 优先、复用与异常处理
  - **变更记录**
3. **文档确认循环**：沟通以文档为准，设计文档的最新版就是当前方案。每次更新文档后展示给用户；用户反馈 → 改文档 → 再展示，循环直到确认。
4. **进入实现**：用户确认前禁止修改代码文件；**用户明确说「直接实现 / 跳过设计」时，跳过提问澄清与确认循环**，以 quick 文档或最小设计记录后进入实现；确认后才进入实现。

## 6. 实现与同步维护（核心）

实现代码时，每完成一项实质进展（一次修改、一个决策、解决一个问题），同步更新 `<slug_dir>` 下相关文档：

- 功能说明：与实际行为保持一致
- 变更记录：追加 `- <YYYY-MM-DD HH:mm>：修改说明`
- 接口/数据结构变更：必须先更新设计文档，再改代码
- 总览增量维护：正式需求（含单点）在首个需求点设计确认后建立 `总览.md` 骨架（章节按 TDD 需求点顺序，单点仅一个章节）；此后每个需求点有进展（设计确认/实现/Review）即同步更新对应章节：状态、关键决策、指向设计文档与 review 文档的链接

**铁律**：代码改了文档没更新 = 工作未完成；实事求是不脑补。

## 7. Review 模式（输出审查文档，subagent 执行）

用户要求 Review（设计或代码）时：

1. 询问 review 设计还是 review 代码；仅审查本次需求相关内容，严禁超纲
2. **优先委托 subagent 执行审查**：
   - 主 agent 用 `spawn_agent` 创建审查子代理；若环境配置了专用审查 agent（如 `ue5-reviewer`，可通过 AGENTS.md 或 agent 列表确认），优先委托给它；否则创建通用审查子代理
   - 向子代理清晰传递：审查类型（设计/代码）、`<slug_dir>` 下相关文档路径、需求上下文、涉及文件路径
   - 子代理负责审查并**落盘报告**到 `<slug_dir>/review/`：
     - 命名：`需求N_标题_设计review.md` 或 `需求N_标题_代码review.md`
     - 同需求报告已存在 → 先读取，在保留历史修复记录的基础上更新，禁止盲目覆盖
     - 内容：标题 / 日期 / 关联需求 / 问题清单（原因、影响面、建议）
   - 环境不支持 subagent 时，主 agent 自行审查并落盘，在报告末尾注明「主 agent 执行」
3. 主 agent 收到落盘结果后，展示报告路径、摘要与问题清单，询问「哪些问题需要现在修复」
4. 修复后再次委托子代理复查并原地更新报告，直至问题清零或用户确认

## 8. 整合模式（按需，替代 consolidate）

触发时机：用户说「整合 / 生成总览」，或里程碑收尾时。

- 读取 `TDD.md`（如有）+ 全部 `需求N_标题.md` + 实际代码 → 刷新 `总览.md`
- 规则：
  - 以代码为准，文档与代码不一致处标注
  - 去重合并；代码中不存在的功能不写入总览
  - 保留重要设计决策（"为什么这样做"）
  - 在对话中输出差异报告（不一致处清单），供用户确认；用户要求时可将差异章节写入 `总览.md`
- **不归档设计文档**：总览 = 聚合视图（当前状态），设计文档保留过程细节，review 文档记录问题

## 9. 总结模式

用户说「总结」时：

- 读取 `总览.md` + 各设计文档（含变更记录）+ review 报告，按需求分组输出：完成项 / 进行中 / 阻塞 / 决策与经验（总览本身是聚合视图，不含各文档变更记录；若总览缺失，直接读原始需求 + 设计文档 + review 报告）
- Review 文档一并纳入总结（问题与已修复项）
- quick 任务不纳入总结
