# 定位

正式需求：整理 → 设计 → 实现 → Review（按需）→ 整合/总结（按需）；Quick：需求文档 → 确认 → 实现。目的：agent 维护文档，而非只写代码或只做设计。

**使用前提**：仅用户显式点名启用，不自动命中。点名后先执行「1 定位」并展示结论；完成前不得讨论内容或改文件。豁免：无文件产出的纯信息问答——可跳过定位文档流；须检索 `<cwd>/.agent/library/`，并在 `.agent/story/` 下跨全部 milestone 查找相关 story（`Archive/` 见约定；忽略各处 `quick/`），结合代码核实后直接回答。一旦需要改文件：重新执行「1 定位」，仅在**当前** milestone 下确认 Quick/正式并落盘（不在其他 milestone 写入）。凡改文件（含元任务改本技能）一律走工作流。

# 约定

```
.agent/milestones.yaml
.agent/library/overall.md
.agent/library/<主题>.md
.agent/story/<milestone>/Archive/
.agent/story/<milestone>/quick/YYYY-MM-DD_任务短语.md
.agent/story/<milestone>/<YYYY-MM-DD_slug>/原始需求.md
.agent/story/<milestone>/<YYYY-MM-DD_slug>/需求N_标题.md
.agent/story/<milestone>/<YYYY-MM-DD_slug>/总览.md
.agent/story/<milestone>/<YYYY-MM-DD_slug>/review/需求N_标题_设计review.md
.agent/story/<milestone>/<YYYY-MM-DD_slug>/review/需求N_标题_代码review.md
```

- `Archive/`：若存在则忽略，不碰触
- `<cwd>`：当前工作目录；`.agent` 固定为 `<cwd>/.agent`，只直接访问该树，禁止扫描其他目录的 `.agent`。路径不存在时停止流程并提醒用户创建 `.agent`
- **代码核实**：允许在当前工程内按入口函数/类名/文件路径线索用 `rg`/`fd` 检索；不因此放开对其它目录 `.agent` 的扫描
- slug：`YYYY-MM-DD_需求slug`，slug 为 ≤5 词中文短语（如 `html文件浏览器`），创建前与用户确认；目录内所有日期统一 `YYYY-MM-DD`
- 命名：文件名模式见路径列表；设计文档编号从 1 起，单点固定 `需求1_标题.md`；quick 不产设计文档
- 变更记录：格式 `- <YYYY-MM-DD HH:mm>：…`；原始需求记需求追加，设计文档记设计变更，总览记多需求点聚合与状态；quick/review 不记；状态小改动更新状态承载文档
- 文档先行：实质性变更（逻辑、接口、数据结构）先更新文档再改代码；文档与代码冲突时以代码为准并标注
- 状态承载：多需求点只写 `总览.md`，单点只写对应设计文档；quick 用自由文本「结果/状态」，不用正式枚举
- 正式需求状态枚举：待设计 / 设计中 / 已确认 / 实现中 / Review 中 / 已完成 / 已Review / 阻塞
- 状态转换：创建前隐式待设计（不落盘）；设计方案首次落盘 → 设计中；设计文档确认 → 已确认；开始实现 → 实现中；实现结束 → 已完成；开始 review → Review 中；代码 review 结束 → 已Review；设计 review 结束 → 设计中或已确认；外部阻塞 → 阻塞（变更记录写明原因与前状态），解除后恢复前状态
- 文档二级标题统一带标号：`## 1. …`、`## 2. …`；总览中多个需求点按出现顺序连续编号，变更记录为最后一节

# Milestone 配置（.agent/milestones.yaml）

```yaml
current: 切片1
milestones:
  切片1:
    created: 2026-05-20
  MS10:
    created: 2026-04-15
```

- `current` 指向当前活跃 milestone；新建/续用 slug 与 quick、以及一切文档与代码相关落盘，默认仅在该 milestone 目录下执行
- 文件不存在时，展示上述模板并确认当前 milestone；用户确认后由 agent 创建，再重新执行定位

# 提问规范（需求与设计澄清）

对影响需求、验收或实现路径的未决策事项坚持访谈直至达成共识。将决策梳理为设计树：每一个决策都会衍生出依附于它的后续决策。已明确的用户需求、可查证事实和纯执行步骤不进入访谈。

- **直接对话**：所有问题、选项、推荐答案和确认请求直接写在普通对话中；禁止调用 `AskQuestion` 或同类提问工具。此规则适用于定位、需求拆分、设计、Review、整合及其他需要用户决策的环节。
- **按轮次处理前沿**：待处理前沿 = 所有前提已确定、可直接提出、无需猜测尚未知晓答案的决策。每轮集中提出整个待处理前沿；用户作答后重算前沿，进入下一轮。若某题答案依赖本轮尚未解决的另一题，则属后续轮次，不得放入本轮。
- **问题格式**（每题）：

❓ **Q1** - **<标题>**: <正文：原因；可多段>

A. …
B. …
C. …

➡️ <推荐答案及原因>

  有可选项时每个选项独占一行；无离散选项时可省略 A/B/C。每轮题号从 Q1 起编。
- **决策权在用户**：每题必须给出推荐答案；用户明确作答时以用户为准；用户未明确回答的问题，一律按该题推荐选项确认，并在进入下一轮或落盘前向用户复述这些默认确认项；禁止脑补推荐之外的未决事实。
- **查证优先（事实由 agent 找）**：可自查的环境事实（文件系统、代码等）由主 agent 直接查（rg/读文件等），不向用户索要；范围大或需并行探索时派子代理。正在进行的探索视为未定前提——仅其下游问题等待子代理报告，其余前沿照常提问，不得因此停滞整轮。
- **结束条件**：前沿为空且用户确认已达成共识时，提问会话结束（设计树分支均已遍历）；此前不得写设计文档、总览或代码。
- **文档纪律**：用户已经明确表达的原始需求或 quick 需求可先整理为草稿并展示确认；未确认的设计细节不写入设计文档或总览，全部确认后一次性落盘，再走文档确认循环。

# 工作流程

## 模式路由（触发词 → 模式）

路由在定位完成后生效。

| 用户触发 | 命中模式 |
|----------|----------|
| 描述新需求 / 「做 XX」 | 1 定位与需求整理 |
| 简单独立任务 / 无规则与接口变更的中小任务（加日志、debug、小改动等） | 2 Quick（先判断是否符合条件，再与用户确认） |
| 「拆分」/ 多需求点大需求 | 3 Design（先判断规模、与用户确认拆分） |
| 「设计」/「写设计文档」 | 3 Design |
| 「实现」/「开工」 | 4 实现与同步维护 |
| 正式需求的「review」/「审查」 | 5 Review（先确认设计或代码） |
| 「整合」/「生成总览」/ 里程碑收尾 / 「总结」 | 6 整合与总结 |
| 「沉淀」/「提炼方法论」/「写入 library」 | 7 知识沉淀 |

## 1. 定位与需求整理

- 检查 `<cwd>/.agent`（访问边界与缺失处理见约定）；不存在则提醒创建并停止
- 读取 `<cwd>/.agent/milestones.yaml` 获取当前 milestone；不存在则按「Milestone 配置」创建后重新执行定位
- 向用户展示定位结论（milestone + 工作目录）；分支确认后补充 slug 或 quick 路径
- 在 `.agent/story/<当前milestone>/` 下查找同主题正式需求 slug（`Archive/` 见约定；同时忽略 `quick/`），并判断任务适合 Quick 还是正式需求；先向用户确认分支，再创建或修改文档（写入仅限当前 milestone）
- **Quick 分支**：输出当前 `<milestone>` 与 `<quick_dir>`，转 2 Quick；不创建 slug，不写 `原始需求.md`
- **正式需求分支**：当前 milestone 下已有同主题 slug 时与用户确认续用并追加需求点；未命中时与用户确认新 slug；输出当前 `<milestone>` 与 `<slug_dir>`
- 拆分/续用是否新增需求点：判定规则见 Design§1，在本步与用户确认
- 仅正式需求整理已明确内容：新 slug 写 `原始需求.md` 并记「初始创建」，续用则追加需求与变更记录；随后同会话进入 Design

**模板：**

```markdown
# 原始需求：<slug 描述>
- <YYYY-MM-DD HH:mm>：初始创建
（后续变更记录继续追加在标题下）
## 1. 需求背景
## 2. 需求描述
## 3. 验收标准
```

## 2. Quick 模式（简单独立任务）

- 适用条件见路由表；路由时与用户确认；中途超范围则暂停并提议转正式需求
- 不建原始需求 / 设计文档；不做 review、不纳入总结；若用户要求 review/整合/总结，说明约束并询问是否转正式需求，确认后重新执行定位
- 流程：写 quick 需求草稿 → 展示确认 → 实现 → 更新结果/状态；**任何代码落地前须经用户确认**（含首轮与实现后的需求变更）。实现后若需求变更：先更新 quick 文档；仍属 Quick 范围则展示变更点并确认后再改代码；超范围则转正式。多轮只同步必要设计偏差。

**模板：**

```markdown
# Quick：<任务短语>
- 日期：YYYY-MM-DD
- 需求：一句话简介
## 1. 方案
## 2. 结果/状态
```

## 3. Design（文档即沟通媒介，含需求拆分）

1. **需求拆分**：规模大（工作流规则/接口/数据结构变更，或跨多文件、超单文件局部；不确定则从严）才新增需求点，须用户确认，不得自行拆分；续用追加同样。中途规模扩大则暂停再确认。本步只确认拆分、不落清单；单点不建总览。定位阶段按本规则确认。
2. **检索设计上下文**：设计前读 `<cwd>/.agent/library/overall.md`（无则跳过；本会话读一次），按主题找子文档，再用 `rg`/`fd` 核实代码。library 仅线索，事实以代码为准。
3. **提问澄清**：按提问规范迭代至共识；此阶段不写设计文档或总览。
4. **落盘设计**：确认后写入 `需求N_标题.md`；状态按约定转换；多需求点更新 `总览.md` 清单，单点在设计文档写状态与关键决策。
5. **文档确认循环**：展示 → 反馈改文档 → 再展示，直至确认；状态按约定转换。设计 review 需改方案时回到本步。
6. **进入实现**：确认前禁止改代码；跳过设计 / 实现门禁见「4 实现」。

**模板：**

```markdown
# 需求N：<标题>
- 状态：<枚举值>（仅单点需求；多需求点省略本行并以总览为准）
- Review：<链接>（仅单点需求且已有报告时）
## 1. 需求简介
一句话。
## 2. 功能说明
策划目标 + 技术行为。
## 3. 设计细节
设计要点（可配 mermaid/伪代码）。
## 4. 变更记录
- <YYYY-MM-DD HH:mm>：初始创建/修改
```

## 4. 实现与同步维护（核心）

**入口门禁：**

- 正式需求：须有 `原始需求.md`、对应设计文档，且状态为「已确认」；大改须用户确认设计。小改仅当用户明确跳过详细设计、已写最小设计记录且状态为「已确认」时可进入
- Quick：须有经用户确认的 quick 文档
- 不满足则回 2 Quick 或 3 Design，不得改代码

**同步检查点：**开始实现、新的实质性设计决策、进入/解除阻塞、实现完成时同步文档；连续小改在下一检查点合并记录。

- 开始 / 完成：状态按约定转换（Quick 同步「结果/状态」）；完成时只同步必要设计偏差与重要决策，不罗列改动文件/实现结果/验证明细；正式需求首次完成时调用 `story-lite-learn`（见 §7）；变更记录按约定
- 实现过程：功能说明与行为一致；接口/数据结构/工作流规则变更按约定「文档先行」
- **实现后需求/设计变更**：先更新设计文档（多点则同步总览）；展示变更并经用户确认后再改代码；状态按约定转换（通常回到设计中或已确认后再进实现中）
- 状态与链接：多需求点更新总览；单点更新设计文档；Quick 更新自身文档

**铁律：**检查点文档未同步 = 工作未完成；实事求是不脑补。

**总览模板：**

```markdown
# 总览：<slug 描述>
## 1. 需求点清单（多需求点）
| 编号 | 名称 | 目标 | 功能范围 | 方案思路 | 依赖 |
|------|------|------|----------|----------|------|
| 1 | … | … | … | … | - |
## 2. 需求点 N：<标题>
- 状态：<枚举值>
- 关键决策：…
- 设计文档：<链接>
- Review：<链接>
## 3. 变更记录
- <YYYY-MM-DD HH:mm>：说明
```

## 5. Review 模式（输出审查文档，必须开子任务）

1. 仅正式需求；Quick 见 §2
2. 询问设计或代码 review；仅审本次范围。设计 review 须有设计文档；代码 review 须状态为「已完成」或「已Review」；否则回 Design/实现。通过后状态按约定转换
3. **必须开子任务**审查并落盘；主 agent 禁止自审。无法开子任务或无可用报告则停止并说明，不回退主审
4. 向子代理传递：审查类型、`<slug_dir>` 相关文档、需求上下文、涉及文件
5. 报告落盘 `<slug_dir>/review/`（命名见约定）；已存在则先读再更新，保留历史修复记录，禁止盲目覆盖
6. 展示路径/摘要/问题清单，问「哪些现在修」；修复后须再开子任务复查并原地更新报告，直至清零或用户确认结束
7. 结束时按约定更新状态与报告链接；保留未修问题与全部历史修复记录

**报告模板：**

```markdown
# 需求N_标题_<设计或代码>review
- 日期：YYYY-MM-DD
- 关联需求：需求N_标题
## 1. 问题清单
| 编号 | 问题 | 原因 | 影响面 | 建议 |
|------|------|------|--------|------|
## 2. 修复记录
```

## 6. 整合与总结

- **范围**：默认当前正式需求 slug；「里程碑收尾」处理当前 milestone 下全部正式需求 slug（`Archive/` 见约定；排除 `quick/`），各 slug 独立整合，不另建里程碑总览
- **多需求点整合**：读总览 + 全部设计文档 + 代码，刷新 `总览.md`
- **单点需求整合**：读原始需求 + 设计文档 + 代码，刷新设计文档，不建 `总览.md`
- **共同规则**：以代码为准并标注差异；去重；不写代码中不存在的功能；保留关键决策；对话输出差异报告，用户要求再写入状态承载文档
- **总结**：多点读总览+设计+review；单点读原始需求+设计+review；按需求分组输出完成项/进行中/阻塞/决策与经验
- **里程碑收尾**：全部正式 slug 处理完后输出里程碑摘要；用户确认即结束；不改 `milestones.yaml`，除非用户要求切换 `current`
- Quick 不进入本模式，见 §2

## 7. 知识沉淀

- **执行者**：调用 `story-lite-learn`；本技能只判触发时机，不内嵌提炼/写入规则
- **完成触发**：正式需求首次完成时调用；单点以首次「已完成」为准，多点以全部「已完成」或「已Review」为准
- **其他触发**：发现可跨需求复用知识时可调用（Quick 完成不强制）；用户触发见路由表；允许再次调用；无可沉淀则只报告、不建文件
