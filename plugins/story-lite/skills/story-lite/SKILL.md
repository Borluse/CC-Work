# 启用

1. 先执行「1 定位」并展示结论。
2. 若定位尚未完成：不得讨论内容、不得改文件。
3. 凡改文件（含元任务改本技能）一律走工作流。

# 做什么

正式需求：整理 → 设计 → 实现 → Review（按需）→ 整合/总结（按需）。Bug：录入 → 根因 → 修复 → 验证。Quick：需求文档 → 确认 → 实现。目的：agent 维护文档，而非只写代码或只做设计。

# 约定

```
.agent/milestones.yaml
.agent/library/overall.md
.agent/library/<主题>.md
.agent/story/quick/<milestone>/任务短语.md
.agent/story/quick/<milestone>/index.yaml
.agent/story/<slug>/原始需求.md
.agent/story/<slug>/总览.md
.agent/story/<slug>/index.yaml
.agent/story/<slug>/<milestone>/需求N_标题.md
.agent/story/<slug>/<milestone>/bug/BugN_标题.md
.agent/story/<slug>/<milestone>/review/需求N_标题_设计review.md
.agent/story/<slug>/<milestone>/review/需求N_标题_代码review.md
```

- `<cwd>`：当前工作目录。`.agent` 固定为 `<cwd>/.agent`。只直接访问该树。禁止扫描其他目录的 `.agent`。
- `<slug_dir>`：`.agent/story/<slug>/`；`<ms_dir>`：`.agent/story/<slug>/<milestone>/`。
- `<quick_doc>`：`.agent/story/quick/<milestone>/任务短语.md`。
- slug：≤5 词中文短语，创建前确认，无日期前缀；`quick` 为保留名。
- 命名：文件名见路径列表。需求点与 Bug 在整个 slug 内分别连续编号；quick 不产设计文档。
- 追踪与取号：正式需求以 `<slug_dir>/index.yaml` 为状态、Review、延续和编号的单一数据源；Quick 以同目录 `index.yaml` 追踪状态。正式 `requirement` / `bug` 是已分配最大编号，新增时递增并追加完整条目。禁止扫描 `<ms_dir>` 取号。旧文件若只有 `需求` / `bug`，读取时兼容 `需求` 为 `requirement`；下一次写入该文件时改为英文键。不批量回填历史条目。延续、无总览单点迁入总览、或整合写入前，若目标 id 尚无 `items` 条目，按总览或设计文档补这一条完整条目。
- 变更记录：`- <YYYY-MM-DD HH:mm>：…`。原始需求记追加。设计记变更。总览记聚合。quick/review 不记。
- 文档先行：实质性变更先更新文档再改代码。文档与代码冲突以代码为准并标注。
- 正式状态枚举：待设计 / 设计中 / 已确认 / 实现中 / Review 中 / 已完成 / 已Review / 阻塞。
- Bug 状态枚举：待确认 / 已确认 / 修复中 / 已修复 / 已验证。
- 状态承载：正式需求写 `items[].status`，Bug 写 `bugs[].status`，Quick 写 `items[].status`。`prior_status` 是状态栈：进入 `Review 中` 或 `阻塞` 时把当前 `status` 追加进去；恢复时弹出末项写回 `status`。旧文件没有对应条目时，仍从总览、设计文档或 Bug 报告读取和更新，直至该 id 被单条补全或后续回填。
- 字段值：`file` 与 Review 字段写相对 `<slug_dir>` 的路径，尚无文件时写 `""`；`continues` / `continued_by` 为需求 id 列表，`prior_status` 为状态字符串列表，皆无则 `[]`。Quick 的 `status` 使用简短状态文字。
- 检索正式 story 时忽略 `.agent/story/quick/`。

## Milestone（`.agent/milestones.yaml`）

```yaml
current: 切片1
milestones:
  切片1:
    created: 2026-05-20
  MS10:
    created: 2026-04-15
```

- `current` 指向当前活跃 milestone。新需求点写入当前 `<ms_dir>`，Quick 写入当前 milestone 的 Quick 目录；已有需求点操作沿用对应 `items[].milestone`，无该条目时用总览里程碑列。
- 若该文件不存在：展示上述模板并确认当前 milestone。用户确认后由 agent 创建，再重新执行定位。
- 若 `<cwd>/.agent` 不存在：停止流程，提醒用户创建 `.agent`。

# 提问规范

对影响需求、验收或实现路径的未决策事项坚持访谈直至达成共识。将决策梳理为设计树：每一个决策都会衍生出依附于它的后续决策。

1. 若事项已是明确的用户需求、可查证事实或纯执行步骤：不进入访谈。
2. 所有问题、选项、推荐答案和确认请求直接写在普通对话中。禁止调用 `AskQuestion` 或同类提问工具。此规则适用于定位、需求拆分、设计、Review、整合及其他需要用户决策的环节。
3. 待处理前沿 = 所有前提已确定、可直接提出、无需猜测尚未知晓答案的决策。每轮集中提出整个待处理前沿。用户作答后重算前沿，进入下一轮。若某题答案依赖本轮尚未解决的另一题：不得放入本轮。用户作答若改了模块归属、同步方式、是否复用已盘点系统，或否定了推荐项里的实现路径，这些都是新前沿；本轮不得落盘或改代码。
4. 每题必须给出推荐答案。若用户明确作答：以用户为准。若用户未明确回答：按该题推荐选项确认，并在进入下一轮或落盘前向用户复述这些默认确认项。禁止脑补推荐之外的未决事实。不得把编译宏、循环依赖、新子系统、跨模块 include 当成已选项的实现细节；这些必须单独成题。
5. 总览或 library 已盘点、且职责相近的现成系统，详细设计访谈必须做成选项。推荐项须说明复用、扩展还是只参考。不得在选项外另发明一套跨模块读数路径。
6. 若前沿为空且用户确认已达成共识：提问会话结束（设计树分支均已遍历）。此前不得写设计文档、总览或代码。
7. 若用户已明确表达原始需求或 quick 需求：可先整理为草稿并展示确认。未确认的设计细节不写入设计文档或总览。全部确认后一次性落盘，再走文档确认循环。

问题格式（每题）。有可选项时每个选项独占一行。无离散选项时可省略 A/B/C。每轮题号从 Q1 起编。题干、选项、推荐不重复已陈述事实。

❓ **Q1** - **<标题>**: <正文：原因；可多段>

A. …
B. …
C. …

➡️ <推荐答案及原因>

# 工作流程

各模式步骤只写本模式动作。写状态：按状态规则把对应 `index.yaml` 条目的 `status` 写成 `<状态>`。无该条目时写总览、设计文档或 Bug 报告。路径、访问、命名、状态承载、文档先行按约定。

## 状态规则

- 正式主链：总览规划新增需求点为 `待设计`，详细设计落盘为 `设计中`；随后 `设计中 → 已确认 → 实现中 → 已完成`。未同步状态即未完成。
- Review：设计 Review 为 `设计中/已确认/Review 中 → Review 中 → 进入前状态`；收尾不因 Review 结束而写成 `已确认`。代码 Review 为 `已完成/已Review/Review 中 → Review 中 → 已Review`。
- Review 例外：无法创建子任务时保持原状态、不改 `prior_status`；进入 `Review 中` 后无可用报告则弹出 `prior_status` 恢复；当前已是 `Review 中` 时复查不再追加栈；改设计回 `设计中` 并清空 `prior_status`，修代码回 `已完成`；当前 Review 字段清空，历史报告保留。
- 设计回退：从 `已确认/实现中/已完成/已Review` 清空 `prior_status` 后回 `设计中 → 已确认 → 实现中 → 已完成`；原状态为 `已Review` 时重做代码 Review。
- 阻塞：把当前 `status` 追加到 `prior_status` 后写 `阻塞`；解除时弹出末项写回。当前已是 `Review 中` 时同样追加，不覆盖更早的栈项。
- Quick：只更新 Quick `index.yaml` 中对应条目的 `status`；Quick Review 不写正式状态。
- Bug：小修走 `已确认 → 修复中 → 已修复 → 已验证`；大修保持 `已确认`，完成 Design 与实现后返回 Bug 写 `已修复 → 已验证`。`待确认` 只作枚举，创建前不落盘；全新需求记录衍生关系后回定位；可复用内容委托 learn。
- 首次 `已完成`：立即调用 `story-lite-learn`。

## 模式路由（触发词 → 模式）

路由在定位完成后生效。

| 用户触发                                          | 命中模式                      |
| --------------------------------------------- | ------------------------- |
| 描述新需求 / 「做 XX」                                | 1 定位与需求整理                 |
| 「报 Bug」/「缺陷」/「崩溃」/「行为异常」/ Review 问题转 Bug      | 3 Bug                     |
| 非 Bug 的简单独立任务 / 无规则与接口变更的中小任务（加日志、debug、小改动等） | 2 Quick（先判断是否符合条件，再与用户确认） |
| 「拆分」/「生成 TDD」/「写 TDD 文档」/「大需求规划」/ 多需求点大需求     | 4 Design（确认范围与拆分，按需整体规划）     |
| 「设计」/「写设计文档」                                  | 4 Design                  |
| 「实现」/「开工」                                     | 5 实现与同步维护                 |
| 正式需求或 Quick 的「review」/「审查」                   | 6 Review（先确认类型与目标）         |
| 「整合」/「生成总览」/ 里程碑收尾 / 「总结」                     | 7 整合与总结                   |
| 「沉淀」/「提炼方法论」/「写入 library」                     | 8 知识沉淀                    |

## 1. 定位与需求整理

入口：启用后第一步。不新增路由优先级。

1. 若本次是无文件产出的纯问答：可跳过定位。检索 `<cwd>/.agent/library/` 及相关 `<slug_dir>` 的跨 milestone 文档。若随后需要改文件：重新定位。
2. 检查 `<cwd>/.agent`。若不存在：按约定停止并提醒。
3. 读取 `milestones.yaml`。若不存在：按约定展示模板、确认后创建，再从步骤 2 重跑定位。
4. 立即展示工作目录与当前 milestone。分支确认后补充 slug、`<slug_dir>`、目标 `<ms_dir>` 或 `<quick_doc>`。
5. 按路由表确认目标模式与路径：
   - 若命中 Bug：关联已有 slug 与目标需求点后转 §3。若没有候选：询问归属。
   - 若命中 Quick：输出 `<quick_doc>` 后转 §2。
   - 若命中 Quick Review：确认当前 milestone 的目标 quick 文档，输出路径后转 §6。
   - 若命中新正式需求：在 `.agent/story/` 下查找同主题 `<slug_dir>`。确认续用或新 slug，并按 §4 步骤 1 确认是否新增需求点。
   - 若命中已有正式需求操作：确认 slug 与目标需求点，从对应 `items` 条目的 `milestone` 定位 `<ms_dir>`；旧文件没有该条目时从总览的里程碑列定位。随后转对应模式。
   - 若命中知识沉淀：转 §8。
6. 若新正式需求已确认：新建 slug 时创建 `<slug_dir>`、`原始需求.md` 与初始内容为 `requirement: 0`、`bug: 0`、`items: []`、`bugs: []` 的 `index.yaml`；续用时追加主题根 `原始需求.md`。随后进入 §4 Design。

## 2. Quick 模式（简单独立任务）

入口：路由时与用户确认。不建原始需求 / 设计文档。不纳入整合/总结。

1. 写 quick 需求草稿并展示，等待确认。确认后创建文档，并在同目录 `index.yaml` 的 `items` 追加 `{ title: <文件名去掉后缀>, status: 已确认 }`；该文件不存在时先以 `items: []` 创建。已有条目则保持其 `status`。
2. 若用户未确认：不改代码。
3. 用户确认本轮后实现，完成后把该条 `status` 写成 `已完成`。
4. 任何代码落地前须经用户确认（含首轮与实现后的需求变更）。
5. 若实现后需求变更：先更新 quick 文档。若仍属 Quick：展示变更点并确认后再改代码。若超范围或中途超范围：暂停，提议转正式需求。
6. 多轮只同步必要设计偏差。
7. 若用户要求整合/总结：询问是否转正式需求。确认后重新执行定位。
8. 若用户要求 Review：转 §6。

## 3. Bug 模式

入口：仅处理已有正式需求 slug。不建新 slug。不使用 quick 文档。

1. 录入与关联
   1. 提取现象、复现步骤、期望行为。若信息不足：先询问。禁止脑补。
   2. 读取 `<slug_dir>` 的原始需求、总览、`index.yaml` 及各 `<ms_dir>` 的设计文档。按需检索其他相关 slug。
   3. 展示 Bug 信息、候选关联文档和原因，等待用户确认。
   4. 若用户确认：从需求条目的 `milestone` 定位 `<ms_dir>`；旧文件没有该条目时从总览定位。将 `index.yaml` 的 `bug` 加一，并向 `bugs` 追加完整条目：`id` 为新编号，`title` 为标题，`req` 为关联需求点 id，`milestone` 为落盘 milestone，`status` 为 `已确认`，`file` 为相对 `<slug_dir>` 的路径，`prior_status` 为 `[]`。再创建 `<ms_dir>/bug/BugN_标题.md`。
2. 根因分析
   1. 结合关联文档、library 线索和实际代码定位根因。事实以代码为准。
   2. 在报告中记录证据、影响范围、拟修改文件和修复方案。
   3. 展示分析与分流结论，等待用户确认。确认前不得改代码。
3. 修复分流
   - 若小修（不改变逻辑分支、接口、数据结构、UE 元数据或需求契约）：按状态规则写 `修复中`，按确认方案实现并验证。
   - 若大修（涉及上述任一变更、跨模块影响或与设计冲突）：按状态规则回 §4 Design，再走 §5 实现，然后返回本模式验证。
   - 若发现全新需求：先在 Bug 报告记录为衍生需求，再按状态规则回 §1。
4. 验证与关闭
   1. 核对代码、Bug 报告和关联需求文档。若设计或契约受影响：须先同步正式文档。
   2. 修复完成：按状态规则写 `已修复`。验证通过：按状态规则写 `已验证`。
   3. 输出 Bug 报告、关联文档、修改文件和验证结果。
   4. 若可跨需求复用：按状态规则转 §8。若无可沉淀：只说明。

## 4. Design（文档即沟通媒介，含需求拆分）

入口：定位后的新正式需求，或路由命中 Design / 拆分 / TDD / 大需求规划。

1. 范围与拆分
   - 若已有多点需求：先确认本次新增或修改的目标需求点。
   - 若规模大（工作流规则/接口/数据结构变更，或跨多文件、超单文件局部；不确定则从严）：才新增需求点。须用户确认。不得自行拆分。续用追加同样。
   - 若单点中途规模扩大：暂停并确认拆分。已有总览则直接扩展；既有无总览单点按步骤 3 迁移状态承载。
   - 跨 milestone 续用 slug 时，新工作在当前 `<ms_dir>` 新建需求点；确认拆分后询问是否改变已有需求点的契约、行为或关键决策。若改变，列出候选旧点并确认回写范围。
   - 本步只确认拆分、不落清单。定位阶段按本规则确认。
2. 检索设计上下文
   - 设计前读 `<cwd>/.agent/library/overall.md`。若不存在：跳过。本会话读一次。按主题找子文档。
   - library 仅线索。事实以代码为准。
3. 总览规划。仅当：新建正式需求，或本次确认新增/拆分需求点，或用户触发拆分/TDD/大需求规划。
   1. 读取主题根 `原始需求.md`、`总览.md`、`index.yaml` 及全部 `<ms_dir>` 的需求点文档。用 `fd`/`rg` 盘点相关系统、模块与基类。保留既有内容。明确复用、扩展和继承关系。
   2. 分类为怪物类或通用系统。若怪物类：关注玩法、技能、制作方案、资源与性能约束。若通用系统：关注核心机制、系统关系、配置方向与关键约束。
   3. 总览规划为独立确认范围。按提问规范补齐该范围的决策后，一次性展示：整体目标与技术约束、系统盘点、需求点清单、实施依赖图和总览结构。
   4. 若用户确认：创建或更新主题根 `总览.md`。每个新增需求点先将 `requirement` 加一，并向 `items` 追加完整条目：`id` 为新编号，`title` 为标题，`milestone` 为 `current`，`status` 为 `待设计`，`file` / `design_review` / `code_review` 为 `""`，`continues` / `continued_by` / `prior_status` 为 `[]`。再以该编号写总览行；其余需求点条目保持不变。
   5. 若既有无总览单点进入总览规划：先按设计文档补全该 id 的 `items` 条目（`status`、`file`、Review 路径从设计文档迁入），再将关键决策迁入总览，并删除设计文档中的对应承载行。随后仅新增或受影响需求点进入详细设计。不生成独立 TDD 文档。

4. 目标需求点详细设计
   - 若单点需求：直接进入。
   - 若已有多点需求且已确认目标：可直接进入。
   - 若刚完成总览规划：仅新增或受影响需求点进入。
   - 每个目标需求点按提问规范独立确认。确认前不写设计文档。至少覆盖：逻辑落在哪个模块/类、表现端如何拿到服务端数据、盘点中的相近系统如何复用或只参考。缺任一项则前沿未空。
5. 落盘设计：按条目的 `milestone` 写入 `<ms_dir>/需求N_标题.md`，使用已占编号且不再增加 `requirement`；把 `file` 写成相对 `<slug_dir>` 的实际路径，状态写 `设计中`。
   - 若已有总览：同步总览中的目标需求点方案。
   - 若为既有无总览单点：在设计文档中写关键决策。
   - 若已确认回写旧点：按旧条目的 `milestone` 定位设计文档，只更新被新点改变的契约、行为或关键决策；旧点状态不变。若旧点尚无 `items` 条目，按总览或设计文档补这一条后再写关系。新条目的 `continues` 加入旧点 id，旧条目的 `continued_by` 加入新点 id。

6. 文档确认循环：展示 → 反馈改文档 → 再展示，直至确认。若用户确认：按状态规则写 `已确认`。用户可在 `设计中` 直接要求设计 Review（§6），不必先确认。若设计 review 需改方案：回到本步更新文档后再复查。
7. 设计确认后停在 `已确认`。用户原话已要求做功能，或之后说了「实现 / 开工」，才进 §5。仅说「确认 / ok / 看起来可以」只确认文档。若设计尚未确认：禁止改代码。跳过详细设计的小改见 §5 门禁。

## 5. 实现与同步维护（核心）

1. 门禁
   - 若正式需求：须有 `原始需求.md`、已确认的设计文档。若不满足：回 §4，不改代码。
   - 若用户明确跳过详细设计的小改：须有已确认的最小设计记录。若不满足：回 §4，不改代码。
   - 若 Quick：须有已确认的 quick 文档，且 Quick `index.yaml` 中该条 `status` 为 `已确认` 或 `已完成`。若不满足：回 §2，不改代码。
2. 同步检查点：开始实现、实质性设计决策、进入/解除阻塞、实现完成时，按状态规则更新。进入阻塞时把当前 `status` 追加到 `prior_status` 再写 `阻塞`；解除时弹出末项写回。Quick 按状态规则更新对应条目。连续小改可合并到下一检查点。未同步即未完成。
3. 实现过程：行为与设计一致。实质性变更按约定文档先行。
4. Quick 实现后需求变更：按 §2。
5. 实质性设计变更：按状态规则回退（清空 `prior_status`，写 `设计中`，对应 Review 字段清空，历史报告保留）。用户只给方向（例如「对齐某某现有系统」）：先回 `设计中`，按提问规范补该方向下的前沿，或展示完整方案草稿。方向词本身不是设计确认，确认前不改代码。确认后再按状态规则走实现。若原状态为 `已Review`：完成后重做代码 review。
6. 完成：状态承载只同步必要设计偏差与重要决策。首次 `已完成`：按状态规则转 §8。

## 6. Review 模式（标准报告，必须开子任务）

入口：先确认类型与目标。只审本次范围。每次审查或复查必须开子任务。

1. 门禁。询问方案/设计或代码 review。正式设计 review 须已有目标设计文档，且状态为 `设计中`、`已确认` 或 `Review 中`；`待设计` 则回 §4 先落盘设计。不要等待用户把设计改成 `已确认`。正式代码 review 须 `已完成`、`已Review` 或 `Review 中`，否则回 §5。当前为 `Review 中` 时按续审进入，不改 `prior_status`。Quick 方案 review 须当前 milestone 的 `index.yaml` 中该条 `status` 为 `已确认` 或 `已完成`；代码 review 须该条为 `已完成`。无该条目或不满足则回 §2。
2. 子任务
   - 正式需求：传递 `<slug_dir>`、目标 `<ms_dir>` 文档、需求上下文和涉及文件。若确认可执行：当前 `status` 不是 `Review 中` 时把当前 `status` 追加到 `prior_status`，再写 `Review 中`。
   - Quick：传递 quick 文档、前次报告上下文和涉及文件。
   - 若无法创建子任务：保持进入前状态（尚未写成 `Review 中` 则不改）。若已写成 `Review 中` 但无可用报告：按状态规则恢复进入前状态。Quick 直接停止并说明。
3. 报告
   - 正式需求且无已有报告：按下方模板写入目标 `<ms_dir>/review/`。
   - 正式需求且已有报告：沿用原格式更新。
   - Quick：默认按同一模板在对话完整输出。不创建报告文件或链接。若用户要求保存：先确认目标路径。
4. 处理。询问哪些问题现在修。
   - 正式需求设计 review 改方案：按状态规则写 `设计中`，清空 `design_review` 与 `prior_status`，按 §4 更新设计文档后复查，不必先写成 `已确认`。
   - 正式需求代码 review 修复后：按状态规则写 `已完成`，清空 `code_review`。
   - Quick：先更新 quick 文档并展示确认。方案修复后直接复查。代码修复在确认后改代码并复查。超出 Quick 或需转 Bug：先转正式需求。
   - 每次复查均开子任务并更新原报告或对话报告，直至清零或用户确认结束。
   - 正式需求转 Bug：携带 Review 结论，并确认关联与修复方案。
5. 收尾。正式设计 review：若 `prior_status` 非空则弹出末项写回 `status`，否则保持当前 `status`；把报告相对路径写入 `design_review`。不因 Review 结束而写成 `已确认`。正式代码 review：写 `已Review`，将 `prior_status` 置为 `[]`，把报告相对路径写入 `code_review`。Quick：只输出最终报告。两者均保留未修问题与全部修复记录。

## 7. 整合与总结

1. 范围。默认当前正式需求 slug。若「里程碑收尾」：处理所有含当前 `<ms_dir>` 的正式 slug（排除 `.agent/story/quick/`）。各 slug 独立整合。不另建里程碑总览。
2. 若存在总览：读主题根总览、`index.yaml` + 全部 `<ms_dir>` 的设计文档 + 代码，生成 `总览.md` 刷新草案。
3. 若为无总览单点：读原始需求、`index.yaml` + 设计文档 + 代码，生成设计文档刷新草案。
4. 整合规则：同时读取相关 Bug 报告作为修正线索。以代码为准并标注差异。去重。不把修复历史直接合入当前设计。不写代码中不存在的功能。保留关键决策。对话输出差异报告。用户确认后写入前：对总览清单或无总览单点中尚无 `items` 的需求点，按总览或设计文档补这一条（`status`、`file`、Review 路径从现有状态行迁入），已有 yaml 条目的 `status` 不改。随后把整合正文按当前总览模板写入；无总览单点按当前需求点模板写入设计文档。
5. 若总结：读 `index.yaml`；存在总览时再读总览+设计+bug+review，无总览单点再读原始需求+设计+bug+review。完成项/进行中/阻塞以 `items[].status` 分组，已关闭 Bug 以 `bugs[].status` 分组；无对应条目时回退总览、设计文档或 Bug 报告。只输出结果，不写文件。
6. 若里程碑收尾：全部正式 slug 处理完后输出里程碑摘要。用户确认即结束。不改 `milestones.yaml`，除非用户要求切换 `current`。
7. Quick 不进入本模式。转正式见 §2。

## 8. 知识沉淀

1. 执行：调用 `story-lite-learn`。主技能只负责触发和跟进。
2. 触发：按状态规则（首次 `已完成`；Bug `已验证` 且可复用）。用户路由或发现可复用知识时也可调用。若无可沉淀：只报告。
3. 跟进：单独展示 learn 预览并等待确认。若未确认且会话继续：在下一收尾点提醒一次。若用户明确跳过：结束跟进。
