# 定位

正式需求：整理 → 设计 → 实现 → Review（按需）→ 整合/总结（按需）；Bug：录入 → 根因 → 修复 → 验证；Quick：需求文档 → 确认 → 实现。目的：agent 维护文档，而非只写代码或只做设计。

**使用前提**：启用后先执行「1 定位」并展示结论；完成前不得讨论内容或改文件。凡改文件（含元任务改本技能）一律走工作流。

# 约定

```
.agent/milestones.yaml
.agent/library/overall.md
.agent/library/<主题>.md
.agent/story/<milestone>/Archive/
.agent/story/<milestone>/quick/YYYY-MM-DD_任务短语.md
.agent/story/<milestone>/<YYYY-MM-DD_slug>/原始需求.md
.agent/story/<milestone>/<YYYY-MM-DD_slug>/需求N_标题.md
.agent/story/<milestone>/<YYYY-MM-DD_slug>/总览.md
.agent/story/<milestone>/<YYYY-MM-DD_slug>/bug/BugN_标题.md
.agent/story/<milestone>/<YYYY-MM-DD_slug>/review/需求N_标题_设计review.md
.agent/story/<milestone>/<YYYY-MM-DD_slug>/review/需求N_标题_代码review.md
```

- `Archive/`：若存在则忽略，不碰触
- `<cwd>`：当前工作目录；`.agent` 固定为 `<cwd>/.agent`，只直接访问该树，禁止扫描其他目录的 `.agent`。路径不存在时停止流程并提醒用户创建 `.agent`
- slug：`YYYY-MM-DD_需求slug`，≤5 词中文短语，创建前确认；目录内日期统一 `YYYY-MM-DD`
- 命名：文件名见路径列表；设计文档与 Bug 各自从 1 自增，单点固定 `需求1_标题.md`；quick 不产设计文档
- 变更记录：`- <YYYY-MM-DD HH:mm>：…`；原始需求记追加，设计记变更，总览记聚合与状态；quick/review 不记
- 文档先行：实质性变更先更新文档再改代码；文档与代码冲突以代码为准并标注
- 状态：多点写 `总览.md`、单点写对应设计文档、quick 用「结果/状态」；状态变更写上述承载处。正式：待设计 / 设计中 / 已确认 / 实现中 / Review 中 / 已完成 / 已Review / 阻塞。Bug（只写对应 Bug 报告）：待确认 / 已确认 / 修复中 / 已修复 / 已验证

# Milestone 配置（.agent/milestones.yaml）

```yaml
current: 切片1
milestones:
  切片1:
    created: 2026-05-20
  MS10:
    created: 2026-04-15
```

- `current` 指向当前活跃 milestone；新建/续用 slug 与 quick、以及一切文档与代码相关落盘，默认仅在该 milestone 目录下执行
- 文件不存在时，展示上述模板并确认当前 milestone；用户确认后由 agent 创建，再重新执行定位

# 提问规范（需求与设计澄清）

对影响需求、验收或实现路径的未决策事项坚持访谈直至达成共识。将决策梳理为设计树：每一个决策都会衍生出依附于它的后续决策。已明确的用户需求、可查证事实和纯执行步骤不进入访谈。

- **直接对话**：所有问题、选项、推荐答案和确认请求直接写在普通对话中；禁止调用 `AskQuestion` 或同类提问工具。此规则适用于定位、需求拆分、设计、Review、整合及其他需要用户决策的环节。
- **按轮次处理前沿**：待处理前沿 = 所有前提已确定、可直接提出、无需猜测尚未知晓答案的决策。每轮集中提出整个待处理前沿；用户作答后重算前沿，进入下一轮。若某题答案依赖本轮尚未解决的另一题，则属后续轮次，不得放入本轮。
- **问题格式**（每题）：

❓ **Q1** - **<标题>**: <正文：原因；可多段>

A. …
B. …
C. …

➡️ <推荐答案及原因>

  有可选项时每个选项独占一行；无离散选项时可省略 A/B/C。每轮题号从 Q1 起编。

- **决策权在用户**：每题必须给出推荐答案；用户明确作答时以用户为准；用户未明确回答的问题，一律按该题推荐选项确认，并在进入下一轮或落盘前向用户复述这些默认确认项；禁止脑补推荐之外的未决事实。
- **结束条件**：前沿为空且用户确认已达成共识时，提问会话结束（设计树分支均已遍历）；此前不得写设计文档、总览或代码。
- **文档纪律**：用户已经明确表达的原始需求或 quick 需求可先整理为草稿并展示确认；未确认的设计细节不写入设计文档或总览，全部确认后一次性落盘，再走文档确认循环。

# 工作流程

## 模式路由（触发词 → 模式）

路由在定位完成后生效。


| 用户触发                                          | 命中模式                      |
| --------------------------------------------- | ------------------------- |
| 描述新需求 / 「做 XX」                                | 1 定位与需求整理                 |
| 「报 Bug」/「缺陷」/「崩溃」/「行为异常」/ Review 问题转 Bug      | 3 Bug                     |
| 非 Bug 的简单独立任务 / 无规则与接口变更的中小任务（加日志、debug、小改动等） | 2 Quick（先判断是否符合条件，再与用户确认） |
| 「拆分」/「生成 TDD」/「写 TDD 文档」/「大需求规划」/ 多需求点大需求     | 4 Design（确认范围与拆分，按需整体规划）     |
| 「设计」/「写设计文档」                                  | 4 Design                  |
| 「实现」/「开工」                                     | 5 实现与同步维护                 |
| 正式需求的「review」/「审查」                            | 6 Review（先确认设计或代码）        |
| 「整合」/「生成总览」/ 里程碑收尾 / 「总结」                     | 7 整合与总结                   |
| 「沉淀」/「提炼方法论」/「写入 library」                     | 8 知识沉淀                    |


## 1. 定位与需求整理

- **纯问答豁免**：无文件产出的问答可跳过定位；检索 `<cwd>/.agent/library/` 及跨 milestone 的相关 story（忽略 `Archive/`、`quick/`）。需要改文件时重新定位，仅在当前 milestone 落盘
- 检查 `<cwd>/.agent` 并读取 `milestones.yaml`；缺失处理见约定和「Milestone 配置」
- 立即展示工作目录与当前 milestone；分支确认后补充 slug 或 quick 路径
- 按路由表确认目标模式与路径：
  - **Bug**：关联当前 milestone 的已有 slug 后转 §3；没有候选时询问归属
  - **Quick**：输出 `<quick_dir>` 后转 §2
  - **新正式需求**：查找同主题需求（忽略 `Archive/`、`quick/`），确认续用或新 slug，并按 Design §1 确认是否新增需求点
  - **已有正式需求操作**：确认当前 milestone 的 slug，转对应模式
  - **知识沉淀**：转 §8
- 新正式需求确认后创建或追加 `原始需求.md`，随后进入 Design

**模板：**

```markdown
# 原始需求：<slug 描述>
- <YYYY-MM-DD HH:mm>：初始创建
（后续变更记录继续追加在标题下）
## 1. 需求背景
## 2. 需求描述
## 3. 验收标准
```

## 2. Quick 模式（简单独立任务）

- 适用条件见路由表；路由时与用户确认；中途超范围则暂停并提议转正式需求
- 不建原始需求 / 设计文档；不做 review、不纳入总结；若用户要求 review/整合/总结，说明约束并询问是否转正式需求，确认后重新执行定位
- 流程：写 quick 需求草稿 → 展示确认 → 实现 → 更新结果/状态；**任何代码落地前须经用户确认**（含首轮与实现后的需求变更）。实现后若需求变更：先更新 quick 文档；仍属 Quick 范围则展示变更点并确认后再改代码；超范围则转正式。多轮只同步必要设计偏差。

**模板：**

```markdown
# Quick：<任务短语>
- 日期：YYYY-MM-DD
- 需求：一句话简介
## 1. 方案
## 2. 结果/状态
```

## 3. Bug 模式

仅处理当前 milestone 下已有正式需求 slug；不建新 slug，不使用 quick 文档。

1. **录入与关联**
  - 提取现象、复现步骤、期望行为；信息不足时先询问，禁止脑补
  - 读取 `<slug_dir>` 的原始需求、设计文档和总览；按需检索当前 milestone 内其他相关 slug
  - 展示 Bug 信息、候选关联文档和原因，等待用户确认
  - 确认后创建 `<slug_dir>/bug/BugN_标题.md`，状态写 `已确认`
2. **根因分析**
  - 结合关联文档、library 线索和实际代码定位根因；事实以代码为准
  - 在报告中记录证据、影响范围、拟修改文件和修复方案
  - 展示分析与分流结论，等待用户确认；确认前不得改代码
3. **修复分流**
  - **小修**：不改变逻辑分支、接口、数据结构、UE 元数据或需求契约；状态改为 `修复中`，按确认方案实现并验证
  - **大修**：涉及上述任一变更、跨模块影响或与设计冲突；先回 4 Design 更新并确认设计，再走 5 实现，完成后返回本模式验证
  - 发现全新需求时记录为衍生需求，回 1 定位与需求整理，不在 Bug 中扩展范围
4. **验证与关闭**
  - 核对代码、Bug 报告和关联需求文档；设计或契约受影响时须先同步正式文档
  - 修复完成写 `已修复`；验证通过写 `已验证`
  - 输出 Bug 报告、关联文档、修改文件和验证结果
  - 根因或修复方式可跨需求复用时，按 8 知识沉淀调用 `story-lite-learn`；无可沉淀则只说明

**Bug 报告模板：**

```markdown
# BugN：<标题>
- 状态：<待确认 / 已确认 / 修复中 / 已修复 / 已验证>
## 1. 复现与期望
## 2. 关联需求
## 3. 根因分析
- 根因：
- 证据：
- 影响范围：
- 修复路径：<小修 / 大修>
## 4. 修复方案与实际修改
## 5. 验证方法与结果
## 6. 变更记录
- <YYYY-MM-DD HH:mm>：初始创建/状态变更
```

## 4. Design（文档即沟通媒介，含需求拆分）

1. **范围与拆分**：已有多点需求先确认本次新增或修改的目标需求点。规模大（工作流规则/接口/数据结构变更，或跨多文件、超单文件局部；不确定则从严）才新增需求点，须用户确认，不得自行拆分；续用追加同样。单点中途规模扩大则暂停并确认拆分，再按第 3 步迁移状态承载。本步只确认拆分、不落清单；单点不建总览。定位阶段按本规则确认。
2. **检索设计上下文**：设计前读 `<cwd>/.agent/library/overall.md`（无则跳过；本会话读一次），按主题找子文档。library 仅线索，事实以代码为准。
3. **大需求整体规划**（仅多需求点，且本次确认拆分或用户触发拆分/TDD/大需求规划时）：
  - 读取 `原始需求.md`、已有 `总览.md` 和全部需求点文档（存在则读取）；用 `fd`/`rg` 盘点相关系统、模块与基类，保留既有内容与状态，并明确复用、扩展和继承关系
  - 分类为怪物类或通用系统；怪物类关注玩法、技能、制作方案、资源与性能约束，通用系统关注核心机制、系统关系、配置方向与关键约束
  - 整体规划为独立确认范围；按提问规范补齐该范围的决策后，一次性展示整体目标与技术约束、系统盘点、需求点清单（含复杂度与风险）、实施依赖图和总览结构
  - 用户确认后直接创建或更新 `总览.md`；新增需求点状态写 `待设计`，设计文档与 Review 链接写 `-`，其余需求点保持原状态
  - 单点扩为多点时，将已有设计文档的状态、从已确认设计中提取的关键决策、设计文档与 Review 链接迁入总览，并删除设计文档中的状态与 Review 行；随后仅新增或受影响需求点进入详细设计，不生成独立 TDD 文档
4. **目标需求点详细设计**：单点需求直接进入；已有多点需求确认目标后可直接进入；整体规划后仅新增或受影响需求点进入。每个目标需求点按提问规范独立确认，确认前不写设计文档，单点不写总览。
5. **落盘设计**：确认后写入目标 `需求N_标题.md`，并在约定的状态承载处写 `设计中`；多点仅同步目标点在总览中的状态、关键决策与设计文档链接，单点在设计文档中写状态与关键决策。
6. **文档确认循环**：展示 → 反馈改文档 → 再展示，直至确认；确认后在状态承载处写 `已确认`。设计 review 需改方案时回到本步。
7. **进入实现**：确认前禁止改代码；跳过设计 / 实现门禁见「5 实现」。

**模板：**

```markdown
# 需求N：<标题>
- 状态：<枚举值>（仅单点需求；多需求点省略本行并以总览为准）
- 关键决策：…（仅单点需求；多需求点写总览）
- Review：<链接>（仅单点需求且已有报告时）
## 1. 需求简介
一句话。
## 2. 功能说明
策划目标 + 技术行为。
## 3. 设计细节
设计要点（可配 mermaid/伪代码）。
## 4. 变更记录
- <YYYY-MM-DD HH:mm>：初始创建/修改
```

## 5. 实现与同步维护（核心）

- **门禁**：正式需求须有 `原始需求.md`、已确认的设计文档；用户明确跳过详细设计的小改，须有已确认的最小设计记录。Quick 须有已确认的 quick 文档；不满足则回 §2/§4，不改代码
- **同步检查点**：开始实现、实质性设计决策、进入/解除阻塞、实现完成时更新约定的状态承载文档；正式需求开始写 `实现中`、完成写 `已完成`，进入阻塞时记录当前状态并写 `阻塞`，解除后恢复所记录状态；Quick 更新「结果/状态」。连续小改可合并到下一检查点；未同步即未完成
- **实现过程**：行为与设计一致；接口、数据结构、工作流规则等实质性变更遵循文档先行；Quick 变更见 §2
- **设计回退**：状态为 `已确认`、`实现中`、`已完成` 或 `已Review` 的正式需求发生实质性设计变更时，在状态承载文档记录原状态，写 `设计中` 并将当前 Review 链接写 `-`，历史报告文件保留；设计确认后写 `已确认`，代码修改时再走 `实现中` → `已完成`；原状态为 `已Review` 时完成后重新执行代码 review
- **完成**：状态承载文档只同步必要设计偏差与重要决策；任一正式需求点首次 `已完成` 时按 §8 调用 `story-lite-learn`

**总览模板：**

```markdown
# 总览：<slug 描述>
## 1. 整体目标与技术约束
## 2. 现有系统盘点
| 系统/模块 | 位置 | 关系 |
|-----------|------|------|
| … | … | 复用/扩展/继承 |
## 3. 需求点清单（多需求点）
| 编号 | 名称 | 目标 | 功能范围 | 方案思路 | 复杂度 | 风险 | 依赖 |
|------|------|------|----------|----------|--------|------|------|
| 1 | … | … | … | … | … | … | - |
## 4. 实施依赖
（使用 mermaid flowchart，并列出实施顺序）
## 5. 需求点 N：<标题>
- 状态：待设计
- 关键决策：…
- 设计文档：-
- Review：-
## 6. 变更记录
- <YYYY-MM-DD HH:mm>：说明
```

## 6. Review 模式（输出审查文档，必须开子任务）

1. **门禁**：仅正式需求；询问设计或代码 review，只审本次范围。设计 review 须状态为「已确认」，代码 review 须状态为「已完成」或「已Review」；否则回 Design/实现
2. **子任务**：每次审查或复查必须开子任务并落盘；传递审查类型、`<slug_dir>` 文档、需求上下文和涉及文件。确认可执行后记录本次进入前状态并写 `Review 中`；无法创建则保持当前状态，执行后无可用报告则恢复本次进入前状态，停止并说明
3. **报告**：新报告按下方模板写入 `<slug_dir>/review/`；已有报告沿用原格式更新，保留历史。展示路径、摘要和问题清单
4. **处理**：询问哪些问题现在修；设计 review 修改方案时写 `设计中`、清除当前 Review 链接，按 Design §6 确认至 `已确认` 后复查；代码 review 修复后写 `已完成`、清除当前 Review 链接，历史报告保留。每次复查均按第 2 步切换状态并原地更新报告，直至清零或用户确认结束。转 Bug 时携带 Review 结论，并确认关联与修复方案
5. **收尾**：设计 review 写 `已确认`，代码 review 写 `已Review`；两者均更新报告链接并保留未修问题与全部历史修复记录

**新报告规则：** 按高→中→低分组（空组省略），`R1` 起全报告连续编号；涉及文件可并列，无则写「无」。

```markdown
# 需求N_标题_<设计或代码>review
- 日期：YYYY-MM-DD
- 关联需求：需求N_标题
## 1. 问题清单

### 🔴 高

- **R1** `path/to/file`
  - 问题：…
  - 原因：…
  - 影响：…
  - 建议：…

### 🟡 中
（同结构；编号续排）

### 🟢 低
（同结构；编号续排）

## 2. 修复记录
```

## 7. 整合与总结

- **范围**：默认当前正式需求 slug；「里程碑收尾」处理当前 milestone 下全部正式需求 slug（`Archive/` 见约定；排除 `quick/`），各 slug 独立整合，不另建里程碑总览
- **多需求点整合**：读总览 + 全部设计文档 + 代码，生成 `总览.md` 刷新草案
- **单点需求整合**：读原始需求 + 设计文档 + 代码，生成设计文档刷新草案
- **整合规则**：同时读取相关 Bug 报告作为修正线索；以代码为准并标注差异；去重；不把修复历史直接合入当前设计；不写代码中不存在的功能；保留关键决策；对话输出差异报告，用户确认后写入对应状态承载文档
- **总结**：多点读总览+设计+bug+review；单点读原始需求+设计+bug+review；按需求分组输出完成项/进行中/阻塞/已关闭 Bug/决策与经验；只输出结果
- **里程碑收尾**：全部正式 slug 处理完后输出里程碑摘要；用户确认即结束；不改 `milestones.yaml`，除非用户要求切换 `current`
- Quick 不进入本模式，见 §2

## 8. 知识沉淀

- **执行**：调用 `story-lite-learn`；主技能只负责触发和跟进
- **触发**：每个正式需求点首次 `已完成` 时立即调用；Bug `已验证` 且存在可复用内容时调用；用户路由或发现可复用知识时也可调用。无可沉淀内容只报告
- **跟进**：单独展示 learn 预览并等待确认；未确认且会话继续时，在下一收尾点提醒一次；用户明确跳过后结束跟进
