# Bug 模式

前置：已完成主技能定位，并已读取主技能的约定、状态规则与模板门禁。

入口：仅处理已有正式需求 slug。不建新 slug。不使用 Quick 文档。

出口：验证通过后把 Bug 状态写为 `已验证`；若发现全新需求则记录衍生关系并回主技能定位。

## 1. 录入与关联

1. 提取现象、复现步骤、期望行为。若信息不足：先询问。禁止脑补。
2. 读取 `<slug_dir>` 的原始需求、总览和 `index.yaml`。按主技能「检索既有设计」检索相关设计；先根据账本确定关联需求点与 milestone，再只深读关联需求点的设计文档；当前 slug 已读文档不因命中再读。
3. 展示 Bug 信息、候选关联文档和原因，等待用户确认。
4. 若用户确认：从需求条目的 `milestone` 定位 `<ms_dir>`；旧文件没有该条目时从总览定位。将 `index.yaml` 的 `bug` 加一，并向 `bugs` 追加：`id` 为新编号，`title` 为标题，`req` 为关联需求点 id，`milestone` 为落盘 milestone，`status` 为 `已确认`，`file` 为相对 `<slug_dir>` 的路径。再创建 `<ms_dir>/bug/BugN_标题.md`。

## 2. 根因分析

1. 结合关联文档、library 线索和实际代码定位根因。事实以代码为准。
2. 在报告中记录证据、影响范围、拟修改文件和修复方案。
3. 展示分析与分流结论，等待用户确认。确认前不得改代码。

## 3. 修复分流

- 若小修（不改变逻辑分支、接口、数据结构、UE 元数据或需求契约）：按状态规则写 `修复中`，按确认方案实现并验证。
- 若大修（涉及上述任一变更、跨模块影响或与设计冲突）：转 `DESIGN.md`，完成设计后转 `IMPLEMENT.md`，然后返回本模式验证。
- 若发现全新需求：先在 Bug 报告记录为衍生需求，再按状态规则回主技能定位。

## 4. 验证与关闭

1. 核对代码、Bug 报告和关联需求文档。若设计或契约受影响：须先同步正式文档。
2. 修复完成：按状态规则写 `已修复`。验证通过：按状态规则写 `已验证`。
3. 输出 Bug 报告、关联文档、修改文件和验证结果。
4. 若可跨需求复用：按 `LEARN.md` 提示沉淀，用户确认后转 `story-lite-learn`。若无可沉淀：只说明。
