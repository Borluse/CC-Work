# 实现与同步维护

前置：已完成主技能定位，并已读取主技能的约定、状态规则与模板门禁；正式需求的设计文档已确认，或 Quick 文档已确认。

入口：设计已确认且用户明确要求开工；或 Quick 条目已确认。

出口：实现完成后把正式需求或 Quick 条目写为 `已完成`；若用户要求 Review，转 `REVIEW.md`。

## 1. 门禁

- 正式需求：须有主题根 `原始需求.md` 与已确认的设计文档，且 `index.yaml` 中该条 `status` 为 `已确认`。
- 用户明确跳过详细设计的小改：须有已确认的最小设计记录。
- Quick：须有已确认的 Quick 文档，且 Quick `index.yaml` 中该条 `status` 为 `已确认` 或 `已完成`。

不满足则转 `DESIGN.md`（或 `QUICK.md`）补齐流程。Story 不运行时否决源码编辑；如已产生代码差异，须先同步设计决策并记录到 `.agent`。

## 2. 同步检查点

在下列时刻必须用状态规则同步状态（账本条目存在时写 `items[].status` 或 `bugs[].status`）：

| 时刻 | 动作 |
|------|------|
| 开始实现 | `实现中` |
| 实质性设计决策 | 同步受影响文档 |
| 进入阻塞 | 把当前 `status` 追加到 `prior_status`，再写 `阻塞` |
| 解除阻塞 | 弹出 `prior_status` 末项写回 `status`（栈空则删该键） |
| 实现完成 | `已完成` |

同步状态按主技能状态规则写入对应账本条目；上表里的状态栈与 Review 路径字段按约定同步整份 `index.yaml`。连续小改可合并到下一检查点。未同步即未完成。

## 3. 实现过程

- 行为必须与设计一致。
- 实质性变更按约定文档先行：先更新设计文档，再改代码。
- 改动源码后，检查相关文档是否需要同步；若产生设计偏差，先同步文档。
- 常规源码检索、实现、测试与静态自查（差异复查、规范核对）都在当前上下文完成。独立审查属于 `REVIEW.md`，由用户触发后执行。

## 4. 实质性设计变更（回退）

当实现中发现设计需要改：

1. 先删除 `prior_status`，然后按状态规则写 `设计中`，对应 Review 路径字段删除（历史报告保留）。
2. 按主技能提问规范补该方向下的前沿，或展示完整方案草稿。
3. 方向词本身不是设计确认（例如「对齐某某现有系统」）。继续实现前应完成确认；如已产生验证性代码差异，确认后同步设计文档。
4. 确认后 `已确认` → 继续实现 → `已完成`。更新设计文档时按约定重抽 `keywords` 并展示差异。
5. 若原状态为 `已Review`：完成后只有用户要求重做代码 Review 才转 `REVIEW.md`；用户未要求时不进入 Review。

## 5. 完成

- 账本与文档只同步必要的设计偏差与重要决策，不逐条复述实现过程。
- 首次到达 `已完成`：仅在存在可跨需求复用的知识时按 `LEARN.md` 提示一次并等用户决定；不自动转入 `story-lite-learn`。用户未要求后续沉淀时本阶段到此结束。
