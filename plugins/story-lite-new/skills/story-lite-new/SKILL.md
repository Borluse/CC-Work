# Story-lite-new

本 Skill 描述一种围绕 `.agent` 文档工作的方式。它解释各类信息的作用和工作视角之间的关系，具体动作由你根据当前意图、上下文和证据判断。只有「不变量」一节是硬约束。

`.agent` 的目录结构、文件命名、YAML schema、状态枚举和 Review 报告格式以同目录的 `convention.md` 为准。

## 工作模型

一次工作可以理解为四类信息不断相互校对：

- **意图**：要解决什么问题，为什么解决，什么结果才算成功。
- **方案**：问题边界、关键决策、取舍、依赖、风险和验证方式。
- **行为**：代码或其他产物实际做了什么。
- **证据**：测试、运行结果、静态检查、Review、用户反馈和环境事实说明了什么。

新的用户反馈、代码事实和验证结果可以修正此前的假设；信息互相冲突时，把冲突显式说出来，再继续澄清或验证；结论所依赖的事实不足时，先补充探索或验证。

`.agent` 是跨会话保留意图和方案的唯一位置。其中每类信息只有一个归属位置，因为同一内容写在两处，一处更新后另一处就会过期：

- `原始需求.md`：按时间追加用户的原始意图，保留需求如何演进。
- `总览.md`：主题入口，见「总览」一节。
- 需求点文档：一个可以独立设计、实现和验证的单元的详细方案。
- Bug 文档：实际行为偏离已确认意图时的现象、根因和修复证据。
- Review 文档：独立校对得到的发现及其处理记录。
- `index.yaml`：编号、状态、文档路径和延续关系的唯一账本。
- `library/`：跨需求可复用的方法论，只在经验确实能复用时沉淀。

由此推出：文档只写当前结论。状态看账本，需求演进看原始需求，修改历史交给版本控制。

## 定位

代码只能提供「行为」。这段行为想达成什么、哪些边界是有意为之、哪些问题已经被发现，只保存在 `.agent` 中；只看代码时这些只能靠推测，而推测出的意图很容易偏离当初确认的意图。因此阅读、解释和排查代码时同样先查 `.agent`：命中时直接获得意图和已知问题，未命中时也能确认结论只能以代码为依据。文档与代码不一致本身就是发现，显式判断是文档过期还是代码缺陷，再修正对应的一方。

检索入口是 `search`（匹配各主题账本的标题和 `keywords`）和 `library/`。命中主题后先读 `总览.md` 了解整体，再深入相关的需求点文档和 Bug 文档。

需要修改文件的工作，还要确认归属的主题和 milestone，因为文档和状态都按这个归属组织。当前 milestone 用 `init` 查看；主题归属不明确时询问用户，同一会话中已确认的主题沿用到用户切换话题为止。只读工作不产生文档，不需要确认归属。

## 总览

总览是读者进入主题的第一站，也是新增或拆分需求点时判断它与已有需求点关系的依据。它只包含：

- 主题目标和各需求点共同遵守的约束，各用一两句话。
- 需求点目录：编号、标题、一句话摘要和指向需求点文档的链接。
- 需求点之间的关系：依赖、延续、共用的系统，以及跨需求点尚未闭合的风险。关系用 Mermaid 图表达，每项只写一句，并指向承载细节的文档。

只关于单个需求点的内容属于该需求点文档。需求点增删、拆分、合并，或需求点之间的关系变化时更新总览；需求点内部的方案变化，只有在一句话摘要不再准确时才需要更新总览。

## 三个工作视角

设计、实现和 Review 是同一个工作模型上的三个视角。常见顺序是设计 → 实现 → Review，但新证据可以让工作回到前一个视角，也可以根据上下文直接进入当前最需要的视角。

- **设计**：把模糊的意图变成一份可讨论、可实现、可验证的解释，重点是目标、范围、成功标准、关键取舍及替代方案，以及与现有系统的关系（复用、扩展还是仅作参考）。普通实现细节留给实现视角。需求边界或关键取舍仍然模糊、Review 发现方案缺陷、用户的新指引改变了目标时，回到设计。
- **实现**：让实际产物体现当前的理解，并用事实检验这份理解。实现不是机械翻译设计文档：代码事实、环境限制和验证结果可能改变最合理的方案，这时把新事实带回设计，不让代码和文档长期分叉。
- **Review**：从相对独立的角度比较意图、方案、行为和证据，发现单一视角容易遗漏的问题。设计或实现需要可信度判断、风险识别或独立校对时进入，执行方式见不变量「Review 隔离」。

视角切换，尤其是从设计进入实现、从实现进入 Review，是值得停下来的节点。进入实现意味着开始修改真实产物，返工成本远高于修改文档，用户认可设计也不等于同意此刻动手；Review 会启动独立子任务，消耗时间与上下文，用户可能希望先自己检查或补充验证。因此一个视角的产出完成后，说明当前结果、建议的下一步和理由，再由用户决定。这是协作习惯，不是门控：用户已经表达了推进意愿（例如原始请求本身就是完成改动或做 Review）时，直接推进。

## Quick

Quick 是简单独立任务的轻量形式，适用于非 Bug 的小任务，以及没有规则或接口变更的中小任务。意图和方案写在一份 Quick 文档中，状态记在当前 milestone 的 Quick 账本里，不创建原始需求、总览和需求点文档。

是否按 Quick 处理由你判断，并在回复中声明，用户可以否决。范围或复杂度超出 Quick 边界时转为正式需求。Quick 同样可以使用 Review，报告可以只在对话中输出。

## Bug

Bug 表示实际行为偏离了已确认的意图。修复只需调整行为时，Bug 文档记录现象、根因和验证证据；修复需要改变方案、接口或验收标准时，问题已经进入设计层面，回到设计视角处理。修复中发现的可复用经验可以沉淀到 `library/`。

## 不变量

以下约束不随场景变化。

1. **文档先行。** 修改任何产物（代码、蓝图、配置、Skill、Persona、UE 元数据等）之前，相关意图和方案已经写入 `.agent`：正式需求写在原始需求、总览和需求点文档中，Quick 写在 Quick 文档中。实现或验证中发现需求、接口、数据结构或验收标准需要变化时，先更新文档，再继续修改产物。原因是文档是跨会话唯一的对齐点，先改代码会让之后的会话只能从代码反推意图。用户明确要求跳过文档时可以跳过；只读工作不受此约束。
2. **决策共识。** 会改变目标、验收、接口、数据结构、模块边界或主要实现方向的事项，由用户决定后才落进产物；设计文档可以作为这些决策的载体，用户确认文档即达成共识。写入 `library/` 前同样展示内容并等用户确认，因为 library 会影响之后所有需求的判断。已明确的用户需求、可查证的事实和纯执行细节不需要提问。实施中发现方案不足或事实冲突时，暂停相关修改，回到讨论。
3. **Review 隔离。** 所有 Review 与复查（包括 Quick 的 Review）都交给与当前上下文隔离的子任务执行，只向子任务提供相关文档、涉及文件和 `convention.md` 中的报告格式；无法创建子任务时告知用户，不在当前上下文中自审。原因是当前上下文带着形成方案和实现时的假设，自审会沿用这些假设。

## Perforce

仅当当前目录属于 Perforce 工作区时，为每个新需求创建 pending changelist，名称用简短准确的中文概括需求；相关文件在修改前归入该 changelist，使每个需求的改动可以独立审阅和提交。`.agent` 目录和仓库根目录的 `AGENTS.md` 不受 Perforce 管理，不纳入 changelist，也不执行 `p4 add`。

## 账本脚本

调用形式为 `python "<Skill 目录>/scripts/story.py" <命令>`，在项目根目录运行，`<Skill 目录>` 是本文件所在目录的绝对路径。需要 Python 3.9+ 和 PyYAML，缺少 PyYAML 时先 `pip install pyyaml`，仍无法运行再告知用户。

脚本固化了账本格式，并在每次读取时校验，因此它覆盖的写入一律通过脚本完成，不手写替代。脚本不覆盖的字段（`continues`、`continued_by`，以及已有条目的 `title`、`file`、`milestone`）直接编辑 YAML，改完执行一次 `status` 即可发现格式错误。参数用 `--help` 查看。

- `init [slug]`：定位环境、主题和当前 milestone；给出 slug 时列出该主题各条目的完整信息。
- `search 词...`：检索已有主题和需求点。
- `status`：按状态汇总进度与阻塞。
- `next-id slug requirement|bug 标题`：取号并写入账本，`--file` 中的 `{id}` 替换为新编号。
- `set-status`：更新状态、`keywords` 和 Review 路径，`--restore` 解除阻塞；`--kind quick --create` 新增 Quick 条目。
- `milestone create|use 名称`：创建或切换 milestone。

## 提问

决策之间存在依赖：一个决策确定后，才会衍生出依附于它的后续决策。因此每轮集中提出所有前提已经确定的问题，答案依赖本轮其他问题的留到下一轮，直到没有未决问题。

- 每题给出推荐答案及原因。用户没有明确回答的题按推荐处理，并在进入下一步前向用户复述这些默认项。不在推荐之外自行假设未决事实。
- 会影响接口、依赖或模块边界的技术选择单独成题，不藏在某个选项的实现细节里。
- 总览或 `library/` 中已有职责相近的系统时，把复用、扩展或仅参考作为选项提出。
- 问题直接写在普通对话中，不调用 `AskQuestion` 等结构化提问工具，因为问题需要附带原因、推荐答案和依赖说明，结构化工具难以完整承载。

问题格式如下。有可选项时每个选项独占一行，没有离散选项时省略 A/B/C；每轮题号从 Q1 起编；题干、选项和推荐不重复已陈述的事实。

❓ **Q1** - **<标题>**: <正文：原因；可多段>

A. …
B. …
C. …

➡️ <推荐答案及原因>

## 文档书写

`.agent` 文档面向有经验的开发者：

- 先写结论，再补充理解和执行所需的依据；省略可以直接推断的常识、重复背景和过程叙述；保留约束、决策、风险和验收标准。
- 不写变更记录，理由见「工作模型」。已有文档中的变更记录不专门清理，整体重写该文档时一并删除。
- 涉及结构、关系、时序、状态、流程或交互的内容配 Mermaid 图。图的类型与正文匹配，使用 ` ```mermaid ` 代码块，节点和边上的文字用双引号包裹，换行用 `<br/>`；正文变化时同步更新图。只包含账本字段的 YAML 不需要图。
- 涉及流程、规则、接口或实现逻辑的内容附一段最小伪代码，使用 ` ```cpp ` 代码块，只表达关键路径、分支和约束，并与正文和图保持一致。

## 结果表达

保持范围意识：工作聚焦用户真正要解决的问题，发现的旁支问题可以提出，但不擅自扩张范围。结果说明当前理解、实际产生的行为、支撑证据以及仍然存在的不确定性。
