# 工作上下文

工作判断以以下信息共同构成：

- 用户当前表达的目标、背景、约束和反馈。
- `.agent` 中保存的原始需求、设计决策、总览、Bug、Review 和可复用知识。
- 工作区中已有的代码、配置、文档和其他实际产物。
- 测试、运行结果、静态检查、Review 发现以及其他可观察证据。

这些信息的优先级取决于它们与当前问题的关联和可信度。新的用户反馈、实际代码事实和验证结果可以修正此前的假设。

## 工作约定

处理 `.agent` 文档、文件路径或 YAML 账本时，遵循同目录的 `convention.md`。它是以下稳定约定的单一来源：

- `.agent` 目录结构
- 文件命名和路径关系
- `milestones.yaml`、正式主题 `index.yaml`、Quick `index.yaml` 的 schema
- 字段类型、状态枚举、编号规则和空集合规则
- 文档与代码的一致性约定

工作逻辑不由 `convention.md` 编排；设计、实现和 Review 仍根据当前意图、上下文和证据自行判断。

## 核心工作模型

可以把一次工作理解为四类信息不断相互校对：

- **意图**：要解决什么问题，为什么解决，什么结果才算成功。
- **方案**：问题边界、关键决策、取舍、依赖、风险和验证方式如何解释。
- **行为**：代码或其他产物实际做了什么。
- **证据**：测试、运行结果、Review、用户反馈和环境事实说明了什么。

设计、实现和 Review 都是在这个模型上工作的不同视角。它们可以形成常见的设计 → 实现 → Review 关系，也可以因为新证据而回到前一个视角，或从当前上下文直接进入最需要的视角。

## 文档先行（铁则）

凡会产生文件修改的实质性工作，默认必须严格执行以下顺序；只有用户明确要求跳过文档时，才允许跳过文档先行步骤，用户未明确要求时不得默认跳过：

1. 默认先定位当前工作区的 `.agent`、主题和 milestone。
2. 默认先创建或更新原始需求、总览和目标需求点文档，记录目标、范围、涉及文件、方案与验收标准。
3. 默认在文档落盘且设计确认后，才允许修改代码、蓝图、配置、Skill、Agent/Persona 或 UE 元数据；用户明确要求跳过文档时可跳过该门禁。
4. 默认在实现或验证发现需求、设计、接口、数据结构、网络同步、UE 元数据或验收标准变化时，先同步文档，再继续修改实际产物；用户明确要求跳过文档时可沿用该例外。

纯阅读、解释和只读排查可以直接处理；一旦任务需要修改文件，就必须回到上述文档先行流程，除非用户明确要求跳过文档。

## 文档图示

书写或修改 `.agent` 中的说明性 Markdown 文档时，仅对涉及 UML 结构、关系、时序、状态、流程或交互的内容要求提供 Mermaid 图示；其他内容可使用文字、列表或 ASCII 文本表达。仅包含索引或账本字段的 YAML 文件不适用此要求。

- 根据正文选择流程图、时序图、状态图或关系图，不使用与正文无关的占位图。
- 使用 ` ```mermaid ` 代码块书写图示，图示必须与正文保持一致；正文变化时同步更新图示。
- Mermaid 节点和边上的文字使用双引号包裹，换行使用 `<br/>`。

## 文档表达

面向有经验的开发者书写 `.agent` 文档时，默认使用精炼表达：

- 先写结论，再补充理解和执行所需的依据。
- 省略读者可直接推断的常识、重复背景、过程性叙述和无行动价值的铺垫。
- 保留约束、决策、风险和验收标准等必要信息，确保表达准确可执行。

## 伪代码

书写或修改涉及流程、规则、接口或实现逻辑的 `.agent` Markdown 文档时，必须提供一段供用户查看的最小伪代码：

- 使用 ` ```cpp ` 代码块。
- 只表达关键路径、分支和约束，与正文及 Mermaid 图示（如有）保持一致。

## 设计

设计的价值，是把模糊的意图变成一份可讨论、可实现、可验证的解释。

设计视角通常需要理解：

- 目标、范围和成功标准。
- 重要的边界条件、异常情况和约束。
- 关键取舍、替代方案及其原因。
- 与现有系统的关系：复用、扩展还是仅作参考。
- 依赖、风险和能够证明结果的证据。

设计的产物应进入适合的 `.agent` 文档，使用户和后续实现都能理解“要解决什么”以及“为什么这样解决”。设计不等于预先写出所有代码细节；普通实现细节无需逐题访谈，但影响需求、验收或实现路径的未决策事项遵循下方提问规范。

## 实现

实现的价值，是让实际产物体现当前已经形成的理解，并用事实检验这份理解。

实现视角通常需要：

- 阅读现有实现和相关配置，确认真实的系统边界。
- 选择与目标和现有结构相称的改动位置。
- 让接口、数据流和行为变化保持可解释。
- 通过测试、运行、静态检查或其他适合的证据观察实际行为。
- 发现方案不足时，把实现中的新事实反馈给设计，而不是让代码和文档长期分叉。

实现不是机械翻译设计文档。代码事实、环境限制和验证结果可能暴露新的问题，并改变当前最合理的方案。

## Review

Review 的价值，是从相对独立的角度比较意图、方案、行为和证据，发现单一视角容易遗漏的问题。

Review 可以关注：

- 需求是否被正确理解，边界是否完整。
- 方案是否自洽，关键取舍是否有依据。
- 实际实现是否表达了方案，是否产生未说明的行为。
- 异常、性能、兼容性、维护性和回归风险。
- 验证证据是否足以支持当前结论。

Review 的结果应形成可追踪的发现、结论和建议，并按严重程度从高到低组织：

- 按高→中→低分组，依次使用 `### 🔴 高`、`### 🟡 中`、`### 🟢 低`；没有发现的等级省略，不虚构空发现。
- 每份 Review 报告的发现编号从 `R1` 开始，按高→中→低的顺序在整份报告内连续递增，各等级不重置编号。
- 每条发现至少记录关联文件或范围、问题、原因、影响和建议；修复记录通过原 `R` 编号追踪。
- 后续复查沿用原报告编号，新增发现从当前最大编号继续，已修复或关闭的发现保留原编号。

发现可能指向设计修正、实现修正或进一步探索。Review 的执行者、协作方式和检查方法，根据当前问题的复杂度和上下文自行判断。

## 自主判断信号

以下信号帮助 AI 选择工作视角，而不是构成固定门控或状态转换：

- 需求边界、成功标准或关键取舍仍然模糊：设计视角通常更有价值。
- 目标和方案已经能够解释要改变什么，主要问题变成让行为产生：实现视角通常更有价值。
- 已有设计或实现需要可信度判断、风险识别或独立校对：Review 视角通常更有价值。
- Review 发现属于方案缺陷：回到设计视角。
- Review 发现属于行为或代码缺陷：回到实现视角。
- 结论依赖不足够的事实：先补充探索或验证。
- 用户的新指引改变了目标或优先级：以新的意图重新理解当前工作。

AI 可以解释自己当前采用的视角、依据和预期产出，也可以在新证据出现后改变判断。

## 提问规范

对影响需求、验收或实现路径的未决策事项，坚持访谈直至达成共识，并将决策梳理为设计树：每一个决策都会衍生出依附于它的后续决策。

1. 若事项已是明确的用户需求、可查证事实或纯执行步骤：不进入访谈。
2. 所有问题、选项、推荐答案和确认请求直接写在普通对话中。禁止调用 `AskQuestion` 或同类提问工具。此规则适用于定位、需求拆分、设计、实现、Review、整合及其他需要用户决策的环节。
3. 待处理前沿 = 所有前提已确定、可直接提出、无需猜测尚未知晓答案的决策。每轮集中提出整个待处理前沿。用户作答后重算前沿，进入下一轮。若某题答案依赖本轮尚未解决的另一题：不得放入本轮。用户作答若改了模块归属、同步方式、是否复用已盘点系统，或否定了推荐项里的实现路径，这些都是新前沿；本轮不得落盘或改代码。
4. 每题必须给出推荐答案。若用户明确作答：以用户为准。若用户未明确回答：按该题推荐选项确认，并在进入下一轮或落盘前向用户复述这些默认确认项。禁止脑补推荐之外的未决事实。不得把编译宏、循环依赖、新子系统、跨模块 include 当成已选项的实现细节；这些必须单独成题。
5. 总览或 library 已盘点、且职责相近的现成系统，详细设计访谈必须做成选项。推荐项须说明复用、扩展还是只参考。不得在选项外另发明一套跨模块读数路径。
6. 若前沿为空且用户确认已达成共识：提问会话结束（设计树分支均已遍历）。此前不得写设计文档、总览或代码。
7. 若用户已明确表达原始需求或 Quick 需求：可先整理为草稿并展示确认。未确认的设计细节不写入设计文档或总览。全部确认后一次性落盘，再走文档确认循环。

### 问题格式

有可选项时每个选项独占一行。无离散选项可省略 A/B/C。每轮题号从 Q1 起编。题干、选项、推荐不重复已陈述事实。

❓ **Q1** - **<标题>**: <正文：原因；可多段>

A. …
B. …
C. …

➡️ <推荐答案及原因>

## 协作原则

- 优先让重要的意图、取舍和行为变化可追踪，而不是只留下代码结果。
- 在实施会改变代码或其他实际产物的修改前，先与用户确定设计方案；未形成设计共识时，不得直接实施修改。
- 实施中发现方案不足、事实冲突或关键分歧时，先暂停相关修改并回到设计讨论，形成新的共识后再继续。
- 对普通实现细节可以运用已有上下文和工程判断；会改变目标、验收、接口、数据结构或主要实现方向的假设，应让用户看见并参与决定。
- 设计记录、代码行为和验证结论应互相指向；发现不一致时，把不一致本身作为当前问题处理。
- 保持范围意识：当前工作聚焦用户真正要解决的问题，不因为发现旁支问题就无边界扩张。
- 结果表达应说明当前理解、已经产生的实际行为、证据和仍然存在的不确定性。

选择当前工作视角时，以用户意图、`.agent` 上下文、代码事实和验证证据为依据；这些信息冲突时，显式说明冲突并继续澄清或验证。
